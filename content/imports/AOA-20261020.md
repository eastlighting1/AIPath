## 세트 A-01 · 로컬 개발 환경에서 모델 호출이 안 된다

**환경:** Docker Desktop (macOS), Docker Model Runner

**지문:** 한 팀이 Docker Desktop이 설치된 맥북에서 사내 챗봇의 로컬 개발 환경을 만들고 있다. 설정의 AI 탭에서 Docker Model Runner를 켜고 `docker model pull ai/smollm2`로 모델을 받았으며, `docker model run ai/smollm2`는 터미널에서 정상적으로 답한다. 그런데 호스트에서 실행하는 파이썬 스크립트, compose로 띄운 컨테이너 안의 API 서버, 브라우저에서 열리는 프런트엔드 개발 서버가 각각 모델 호출에 실패한다. 아래는 팀이 모은 호출 주체별 정보다. 각 질문은 서로 다른 호출 주체를 다룬다.

| 호출 주체 | 실행 위치 | 비고 |
| --- | --- | --- |
| 파이썬 스크립트 | 호스트 프로세스 | OpenAI SDK 사용, 문서에 나온 포트 12434로 접속 시도 |
| API 서버 | compose 컨테이너 | 모델 러너 주소를 환경 변수로 받아 호출 |
| 프런트엔드 | 브라우저 (`http://localhost:3131`에서 제공) | 모델 러너 API를 직접 호출 |

### A-01-1 · 호스트 스크립트의 연결 거부

단일 선택 · 케이스 · 도메인 ① · L1 · 제품: Docker

호스트의 파이썬 스크립트가 `localhost:12434`로 접속할 때 다음 오류가 난다. 같은 PC에서 `docker model run ai/smollm2`는 정상 동작한다.

```text
httpx.ConnectError: [Errno 61] Connection refused
  while connecting to localhost:12434
```

이 증상을 해결하는 조치는 무엇인가?

A. `docker model install-runner`를 다시 실행해 러너를 재설치한다.

B. 스크립트의 접속 주소를 `http://model-runner.docker.internal`로 바꾼다.

C. Docker Desktop 설정의 AI 탭에서 호스트 측 TCP 지원(Enable host-side TCP support)을 켜고 포트를 지정한다.

D. 모델을 `ai/smollm2:360M-Q4_K_M` 태그로 다시 pull 한다.

E. `OPENAI_API_KEY` 환경 변수를 설정한 뒤 스크립트를 다시 실행한다.

**정답: C**

**상세 해설**

A. `docker model run`이 이미 동작하므로 러너는 설치되어 돌고 있다. 문제는 러너 설치가 아니라 호스트 프로세스가 TCP로 접근할 수 있는지 여부다.

B. 이 주소는 컨테이너에서 모델 러너에 접근할 때 쓰는 주소다. 호스트 프로세스는 `localhost`와 TCP 포트로 접근한다.

C. 호스트 프로세스가 `http://localhost:12434`로 접근하려면 호스트 측 TCP 지원을 켜야 한다. 이 옵션을 켜지 않으면 해당 포트가 열리지 않아 연결이 거부된다.

D. 모델 태그는 CLI에서 이미 응답을 받는 상황과 무관하다. 연결 단계에서 거부되는 증상이므로 모델 이미지 문제가 아니다.

E. DMR은 `Authorization` 헤더를 무시하며 API 키를 요구하지 않는다. 또한 연결 거부는 인증 이전의 TCP 접속 단계 오류다.

### A-01-2 · 컨테이너에서 모델 러너로 가는 주소

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

compose로 띄운 API 서버 컨테이너가 Docker Desktop의 모델 러너에 접근해야 한다. 경로 부분을 제외한 서버 주소로 문서가 안내하는 값은 무엇인가?

A. `http://model-runner.docker.internal`

B. `http://localhost:12434`

C. `http://172.17.0.1:12434`

D. 호스트의 Docker 유닉스 소켓 파일

E. `http://model-runner.docker.internal:12434`

**정답: A**

**상세 해설**

A. Docker Desktop에서 컨테이너가 모델 러너에 접근하는 기본 주소는 포트 없이 `http://model-runner.docker.internal` 이다.

B. 컨테이너 안의 `localhost`는 컨테이너 자신을 가리킨다. 이 주소는 호스트 프로세스가 TCP로 접근할 때의 주소다.

C. 이 주소는 Docker Engine 환경에서 컨테이너가 접근할 때 문서가 안내하는 값이다. Docker Desktop 표의 컨테이너용 주소가 아니다.

D. 유닉스 소켓 방식은 호스트에서 `curl --unix-socket`으로 호출할 때 문서에 나온 방법이다. 컨테이너용 기본 주소가 따로 있다.

E. 포트를 붙인 형태는 Docker Engine에서 `extra_hosts`로 `host-gateway`를 매핑했을 때 문서가 안내하는 형태다. Desktop 컨테이너용 주소는 포트가 없는 형태다.

### A-01-3 · 브라우저 프런트엔드의 CORS 차단

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

프런트엔드 개발 서버가 `http://localhost:3131`에서 제공되고, 같은 PC의 터미널에서 `curl http://localhost:12434`로 모델 러너에 접근하면 응답이 온다. 그러나 브라우저 콘솔에는 모델 러너 API 호출이 CORS 정책 위반으로 차단됐다는 오류가 찍힌다. 어떻게 해결하는가?

A. 프런트엔드의 요청에 `Authorization` 헤더로 API 키를 실어 보낸다.

B. `docker model configure --context-size 8192 ai/smollm2`를 실행한다.

C. 프런트엔드의 접속 주소를 `http://model-runner.docker.internal`로 바꾼다.

D. 호스트 측 TCP 포트를 80으로 바꾼다.

E. 호스트 측 TCP 설정의 CORS 허용 출처(CORS Allows Origins)에 프런트엔드가 제공되는 출처 `http://localhost:3131`을 추가한다.

**정답: E**

**상세 해설**

A. DMR은 `Authorization` 헤더를 무시한다. CORS 차단은 모델 러너가 허용한 출처 목록의 문제이므로 헤더를 추가해도 달라지지 않는다.

B. `--context-size`는 모델의 컨텍스트 크기 설정이다. 요청을 허용할 출처와 관련이 없다.

C. 그 주소는 컨테이너에서 쓰는 주소다. 브라우저는 호스트 프로세스이고 호스트 프로세스는 `localhost`와 TCP 포트로 접근한다.

D. 포트 번호를 바꿔도 요청 출처가 허용 목록에 들어가지는 않는다. CORS는 출처 허용 여부로 판단된다.

E. 문서는 로컬 프런트엔드 웹 앱에서 모델 러너를 직접 호출한다면 CORS 허용 출처에서 웹 앱이 실행되는 URL(예: `http://localhost:3131`)을 선택하라고 안내한다.

### A-01-4 · OpenAI SDK 설정값

단일 선택 · 케이스 · 도메인 ① · L1 · 제품: Docker

호스트에서 TCP 접근이 가능한 상태다. 개발자가 OpenAI 파이썬 SDK로 모델 러너의 `ai/smollm2`를 호출하려 한다. 다음 중 문서에 맞는 `base_url`과 `api_key` 조합은 무엇인가?

```python
client = OpenAI(base_url=<값 1>, api_key=<값 2>)
```

A. 값 1 = `http://localhost:12434/v1`, 값 2 = 임의의 자리표시 문자열

B. 값 1 = `http://localhost:12434/engines/v1`, 값 2 = 임의의 자리표시 문자열

C. 값 1 = `http://localhost:12434/engines/v1/chat/completions`, 값 2 = 임의의 자리표시 문자열

D. 값 1 = `http://model-runner.docker.internal/engines/v1`, 값 2 = 임의의 자리표시 문자열

E. 값 1 = `http://localhost:12434/engines/v1`, 값 2 = DMR이 검증하므로 DMR 전용으로 발급한 키

**정답: B**

**상세 해설**

A. OpenAI 호환 엔드포인트는 `/engines/v1` 아래에 있다. 문서가 OpenAI SDK용으로 안내하는 기본 URL은 `/v1` 단독이 아니다.

B. 문서는 OpenAI SDK용 기본 URL로 `http://localhost:12434/engines/v1`을 안내하고, DMR이 API 키를 요구하지 않으므로 SDK 예시에서 `api_key`에 자리표시 값을 넣는다.

C. `base_url`은 엔드포인트 앞부분까지만 준다. SDK가 `/chat/completions`를 스스로 덧붙이므로 전체 엔드포인트 경로를 넣지 않는다.

D. 이 주소는 컨테이너용 주소다. 호스트에서 실행하는 SDK는 `localhost`와 TCP 포트를 쓴다.

E. DMR은 API 키를 요구하지 않고 `Authorization` 헤더를 무시하므로 전용 키를 발급할 필요가 없다.

## 세트 A-02 · 모델 주소를 하드코딩하지 않는다

**환경:** Docker Compose, Docker Model Runner

**지문:** AI 서비스 팀은 개발자마다 다른 모델 주소를 컨테이너 환경 변수에 직접 적던 방식을 버리고, compose.yaml의 `models` 최상위 요소로 모델을 선언해 주소와 이름을 주입받게 하려 한다. 백엔드 `app` 서비스는 채팅 모델과 임베딩 모델을 쓰며, 일부 코드는 이미 `AI_MODEL_URL` 같은 정해진 환경 변수 이름을 읽는다. 아래는 팀이 정리한 초안 일부와 CI 러너의 상태다. 각 질문은 서로 다른 주제를 다룬다.

```yaml
# compose.yaml 초안
services:
  app:
    image: registry.example.com/chat-app:1.4
    models:
      - chat-llm
      - embedding-model
models:
  chat-llm:
    model: ai/smollm2
  embedding-model:
    model: ai/all-minilm
```

```text
# CI 러너
$ docker compose version
Docker Compose version v2.35.1
```

### A-02-1 · 짧은 문법으로 주입되는 환경 변수

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

위 초안을 지원하는 환경에서 그대로 `docker compose up` 했을 때, `app` 컨테이너에 주입되는 모델 관련 환경 변수 이름은 무엇인가?

A. `MODELS_CHAT_LLM`, `MODELS_EMBEDDING_MODEL` 두 개

B. `CHAT-LLM_URL`, `CHAT-LLM_MODEL`, `EMBEDDING-MODEL_URL`, `EMBEDDING-MODEL_MODEL`

C. `CHAT_LLM_URL`, `CHAT_LLM_MODEL`, `EMBEDDING_URL`, `EMBEDDING_MODEL`

D. `CHAT_LLM_URL`, `CHAT_LLM_MODEL`, `EMBEDDING_MODEL_URL`, `EMBEDDING_MODEL_MODEL`

E. `CHAT_LLM_ENDPOINT`, `CHAT_LLM_NAME`, `EMBEDDING_MODEL_ENDPOINT`, `EMBEDDING_MODEL_NAME`

**정답: D**

**상세 해설**

A. 짧은 문법은 모델마다 접속 주소(`_URL`)와 모델 식별자(`_MODEL`) 두 변수를 만든다. 모델당 변수 하나가 아니다.

B. 환경 변수 이름에는 하이픈을 쓰지 않는다. 문서의 예에서 `embedding-model`은 대문자와 밑줄로 바뀐 `EMBEDDING_MODEL_URL`이 된다.

C. 접두사는 모델 이름 전체(`EMBEDDING_MODEL`)다. 이름 일부를 잘라낸 `EMBEDDING_URL`은 `endpoint_var`로 직접 지정해야 생기는 형태다.

D. 짧은 문법은 모델 이름을 대문자와 밑줄로 바꾼 접두사에 `_URL`, `_MODEL`을 붙인 변수를 주입한다. `embedding-model`은 `EMBEDDING_MODEL_URL`, `EMBEDDING_MODEL_MODEL`이 된다.

E. `_ENDPOINT`, `_NAME` 접미사는 기본 규칙이 아니다. 기본 접미사는 `_URL`과 `_MODEL`이며, 다른 이름은 긴 문법에서 직접 지정한다.

### A-02-2 · CI 러너에서 models 요소가 인식되지 않는다

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

위 CI 러너(Compose v2.35.1)에서 초안을 검증하면 `models` 최상위 요소를 처리하지 못해 실패한다. 문서 기준으로 올바른 조치는 무엇인가?

A. 모델 선언을 `provider` 서비스 방식으로 바꿔 Compose 버전 문제를 피한다.

B. Compose를 `models` 요소를 지원하는 v2.38 이상으로 올린다.

C. Docker Engine만 최신 버전으로 올리고 Compose는 그대로 둔다.

D. 파일 맨 위에 `version: "2.38"`을 추가한다.

E. 각 모델에 `context_size`를 지정해 요소를 활성화한다.

**정답: B**

**상세 해설**

A. `provider` 서비스도 Compose 2.36 이상이 필요해 v2.35.1에서는 해결되지 않는다. 또 문서는 AI 모델에는 `provider`보다 `models` 최상위 요소를 쓰라고 안내한다.

B. 문서가 밝힌 `models` 요소의 전제 조건은 Docker Compose v2.38 이상이다. 러너의 Compose를 올려야 한다.

C. 요건은 Compose 버전으로 명시되어 있다. Engine 버전을 올려도 Compose가 v2.35.1이면 그대로다.

D. 최상위 `version` 속성은 더 이상 쓰지 않는 정보성 필드이며 기능 활성화에 쓰이지 않는다. 쓰면 오히려 obsolete 경고가 나온다.

E. `context_size`는 모델의 최대 컨텍스트 크기를 정하는 선택 속성이다. 요소 지원 여부와 무관하다.

### A-02-3 · 기존 변수 이름을 유지하면서 주소를 주입

단일 선택 · 케이스 · 도메인 ① · L3 · 제품: Docker

Compose를 지원 버전으로 올렸다고 하자. 애플리케이션 코드는 수정할 수 없고 다음 이름의 환경 변수를 읽는다: 채팅 모델은 `AI_MODEL_URL`(주소)과 `AI_MODEL_NAME`(모델 식별자), 임베딩 모델은 `AI_EMB_URL`과 `AI_EMB_NAME`. 모델 주소를 compose 파일에 하드코딩해서도 안 된다. 초안의 키 이름은 `chat-llm`과 `embedding-model`이다. 이 조건을 모두 만족하는 구성은 무엇인가?

A.

```yaml
services:
  app:
    models:
      chat-llm:
        endpoint_var: AI_MODEL_URL
        model_var: AI_MODEL_NAME
      embedding-model:
        endpoint_var: AI_EMB_URL
        model_var: AI_EMB_NAME
models:
  chat-llm:
    model: ai/smollm2
  embedding-model:
    model: ai/all-minilm
```

B.

```yaml
services:
  app:
    models: [chat-llm, embedding-model]
models:
  chat-llm:
    model: ai/smollm2
    endpoint_var: AI_MODEL_URL
    model_var: AI_MODEL_NAME
  embedding-model:
    model: ai/all-minilm
    endpoint_var: AI_EMB_URL
    model_var: AI_EMB_NAME
```

C.

```yaml
services:
  app:
    models: [ai_model, ai_emb]
models:
  ai_model:
    model: ai/smollm2
  ai_emb:
    model: ai/all-minilm
```

D.

```yaml
services:
  app:
    models: [chat-llm, embedding-model]
    environment:
      AI_MODEL_URL: http://model-runner.docker.internal/engines/v1
      AI_MODEL_NAME: ai/smollm2
      AI_EMB_URL: http://model-runner.docker.internal/engines/v1
      AI_EMB_NAME: ai/all-minilm
```

E.

```yaml
services:
  app:
    models:
      chat-llm:
        endpoint_var: AI_MODEL_NAME
        model_var: AI_MODEL_URL
      embedding-model:
        endpoint_var: AI_EMB_NAME
        model_var: AI_EMB_URL
```

**정답: A**

**상세 해설**

A. `endpoint_var`와 `model_var`는 서비스의 `models` 항목(긴 문법)에서 주소 변수와 모델 식별자 변수의 이름을 지정한다. 최상위 `models`에는 모델 정의만 두므로 주소를 하드코딩하지 않고도 기존 변수 이름을 유지한다. 이 형태는 `docker compose config`로 문법을 확인했다.

B. `endpoint_var`, `model_var`를 최상위 모델 정의에 두면 스키마가 허용하지 않는다. `docker compose config`가 `models.llm additional properties 'endpoint_var', 'model_var' not allowed`와 같은 오류를 낸다.

C. 짧은 문법으로 모델 이름을 `ai_model`로 지으면 `AI_MODEL_URL`은 생기지만 모델 식별자는 `AI_MODEL_MODEL`이 되어 `AI_MODEL_NAME`과 맞지 않는다.

D. 주소와 모델 이름을 `environment`에 직접 적는 방식이라 하드코딩 금지 조건을 어긴다. 또한 모델 정의가 빠져 있다.

E. `endpoint_var`에는 주소가, `model_var`에는 모델 식별자가 담긴다. 둘을 반대로 지정하면 코드가 읽는 값이 뒤바뀐다.

### A-02-4 · 임베딩 모델 구성

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

임베딩 모델 `ai/all-minilm`으로 `/v1/embeddings` 엔드포인트를 쓰려는데 임베딩 호출이 제대로 구성되지 않는다. 초안에서 임베딩 모델에 대한 설정은 `model: ai/all-minilm` 한 줄뿐이다. 문서에 맞는 수정은 무엇인가?

A. 최상위 `models`의 임베딩 모델에 `context_size: 4096`을 늘려서 지정한다.

B. `app` 서비스의 `command`에 `--embeddings`를 추가한다.

C. 서비스의 `models` 항목에 `model_var: EMBEDDING_MODEL`을 지정한다.

D. `model:` 값을 `ai/all-minilm --embeddings` 형태로 바꾼다.

E. 최상위 `models`의 임베딩 모델에 `runtime_flags: ["--embeddings"]`를 추가한다.

**정답: E**

**상세 해설**

A. `context_size`는 최대 토큰 컨텍스트 크기다. 임베딩 엔드포인트에 필요한 조건은 컨텍스트 크기가 아니라 `--embeddings` 플래그다.

B. `command`는 앱 컨테이너 프로세스에 전달되는 인자다. 추론 엔진을 시작할 때 쓰는 플래그는 모델 정의의 `runtime_flags`로 준다.

C. `model_var`는 모델 식별자를 담을 환경 변수의 이름을 정할 뿐 모델 러너의 동작 설정이 아니다.

D. `model`은 OCI 아티팩트 식별자다. 거기에 명령행 플래그를 이어 쓰는 방식은 정의되어 있지 않다.

E. 문서는 `/v1/embeddings` 엔드포인트에 임베딩 모델을 쓰려면 `--embeddings` 런타임 플래그를 반드시 포함하라고 하며, `runtime_flags`는 추론 엔진 시작 시 전달되는 플래그 목록이다.

## 세트 A-03 · GPU 서비스가 기동하지 않는다

**환경:** Docker Compose (NVIDIA GPU 4장 서버)

**지문:** 추론 서버는 NVIDIA 드라이버가 설치된 GPU 4장(인덱스 0\~3)을 가진 호스트다. 팀원들이 서비스별로 compose.yaml의 `deploy.resources.reservations.devices`에 GPU 예약을 따로 작성했는데, 일부는 `docker compose`가 설정을 거부하고 일부는 의도와 다른 수의 GPU를 가져간다. 아래는 서비스별 요구사항이다. 각 질문은 서로 다른 서비스 하나를 다루며 해당 질문에 그 서비스의 정의가 나온다.

| 서비스 | 요구사항 |
| --- | --- |
| llm-a | GPU 1장 |
| llm-b | 0번과 3번 GPU만 사용 |
| llm-c | 호스트의 GPU 4장 모두 사용 |
| embedder | GPU 1장 |

### A-03-1 · 설정 검증이 거부된다

단일 선택 · 케이스 · 도메인 ① · L1 · 제품: Docker

`llm-a`의 정의는 다음과 같고, 검증 단계에서 오류가 난다.

```yaml
services:
  llm-a:
    image: nvidia/cuda:12.9.0-base-ubuntu22.04
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
```

```text
validating compose.yaml: services.llm-a.deploy.resources.reservations.devices.0
missing property 'capabilities'
```

수정 방법은 무엇인가?

A. `count: 1`을 `device_ids: ['0']`로 바꾼다.

B. 같은 `devices` 항목에 `capabilities: [gpu]`를 추가한다.

C. `driver: nvidia` 줄을 삭제한다.

D. `options`에 `gpu: true`를 추가한다.

E. `reservations`를 `limits`로 바꿔 GPU 장치를 정의한다.

**정답: B**

**상세 해설**

A. `device_ids`는 어느 GPU인지를 지정하는 필드이고 `capabilities`를 대신하지 못한다. `capabilities` 누락 오류는 그대로 남는다.

B. `capabilities`는 `devices` 항목의 유일한 필수 필드이며 `[gpu]`처럼 문자열 목록으로 지정한다. 이 필드가 없으면 서비스 배포에서 오류가 난다.

C. `driver`는 선택 필드다. 필수 필드인 `capabilities`가 없다는 오류는 `driver`를 지운다고 해결되지 않는다.

D. `options`는 드라이버별 키-값 설정을 전달하는 필드이며 `capabilities`를 대체하지 않는다.

E. 문서의 GPU 장치 예약 위치는 `deploy.resources.reservations.devices`다. 위치를 옮긴다고 필수 필드가 채워지지 않는다.

### A-03-2 · 0번과 3번 GPU만 사용

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

`llm-b`의 정의는 다음과 같고 설정 검증 단계에서 `"count" and "device_ids" attributes are exclusive` 오류가 난다.

```yaml
services:
  llm-b:
    image: registry.example.com/llm-b:3.1
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 2
              device_ids: ['0', '3']
              capabilities: [gpu]
```

0번과 3번 GPU만 쓴다는 요구사항을 지키면서 오류를 없애는 수정은 무엇인가?

A. `count: 2`를 `count: all`로 바꾼다.

B. `device_ids`를 지우고 `count: 2`만 남긴다.

C. `capabilities`에 `nvidia-compute`를 추가한다.

D. `count`를 지우고 `device_ids: ['0', '3']`만 남긴다.

E. `count: 2` 항목과 `device_ids: ['0', '3']` 항목을 `devices` 목록에 별도 항목 두 개로 나눈다.

**정답: D**

**상세 해설**

A. `count`와 `device_ids`는 함께 정의할 수 없다. 값을 `all`로 바꿔도 두 필드가 같이 있어 같은 오류가 난다.

B. `count: 2`는 GPU 두 장을 예약할 뿐 어느 GPU인지 지정하지 못한다. 0번과 3번만 쓴다는 요구사항을 보장하지 못한다.

C. 오류의 원인은 `capabilities`가 아니라 `count`와 `device_ids`의 동시 정의다. 기능 목록을 늘려도 해결되지 않는다.

D. `count`와 `device_ids`는 서로 배타적이므로 하나만 정의해야 한다. 특정 GPU를 지정해야 하므로 `device_ids`를 남긴다.

E. `count` 항목은 어떤 GPU인지 지정하지 못하므로, 나눠서 정의하면 0번과 3번만 쓴다는 요구사항을 보장하지 못한다.

### A-03-3 · 호스트보다 많은 GPU 요청

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

`llm-c`는 호스트 GPU 4장을 모두 써야 한다. 다음 정의로 실행하면 기동이 실패한다.

```yaml
services:
  llm-c:
    image: registry.example.com/llm-c:1.0
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 8
              capabilities: [gpu]
```

실패 원인과 수정으로 옳은 것은 무엇인가?

A. 오류를 피하려고 `device_ids: ['0','1','2','3']`을 `count: 8`과 함께 정의한다.

B. `capabilities` 값을 `all`로 바꿔 모든 기능을 요청한다.

C. 호스트에 있는 GPU 수(4)보다 큰 `count` 값이 오류의 원인이므로, `count`를 호스트 GPU 수인 4로 낮춘다.

D. `replicas: 2`를 지정해 GPU 요청을 두 컨테이너로 나눈다.

E. `driver`를 `amd`로 바꾼다.

**정답: C**

**상세 해설**

A. `count`와 `device_ids`는 동시에 쓸 수 없다. 오류가 하나 더 늘 뿐이다.

B. `capabilities`는 요청할 장치 기능(`gpu` 등)의 목록이다. GPU 개수와 무관하다.

C. 문서는 호스트의 GPU 수보다 큰 `count`를 쓰면 오류가 난다고 설명한다. 4장이 필요하므로 `count: 4`로 맞춘다.

D. `count` 제한은 각 컨테이너의 예약에 적용된다. 컨테이너를 늘려도 한 컨테이너의 `count: 8` 오류는 사라지지 않는다.

E. NVIDIA GPU 호스트에서 `amd` 드라이버를 지정하면 GPU를 예약할 수 없다. `count` 초과와도 무관하다.

### A-03-4 · `count`와 `device_ids`가 모두 없을 때

단일 선택 · 케이스 · 도메인 ① · L2 · 제품: Docker

`embedder`는 GPU 1장만 써야 하는데 팀원이 아래처럼 정의했다. `docker compose config` 검증은 오류 없이 통과한다.

```yaml
services:
  embedder:
    image: registry.example.com/embedder:1.2
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              capabilities: [gpu]
```

이 정의로 기동하면 `embedder`에 할당되는 GPU는 몇 장인가?

A. 호스트의 GPU 4장 모두

B. 1장

C. 0장. `count`가 없으면 예약이 이루어지지 않는다.

D. 설정 검증 오류. `count` 또는 `device_ids` 중 하나는 반드시 있어야 한다.

E. 인덱스 0번 GPU 1장

**정답: A**

**상세 해설**

A. 문서에 따르면 `count`가 없거나 `all`이면 호스트의 모든 GPU를 사용하고, `device_ids`가 없어도 호스트의 모든 GPU를 사용한다. 둘 다 없으므로 4장 전부 쓴다. 1장만 쓰려면 `count: 1`을 명시해야 한다.

B. 1장은 `count: 1`을 명시했을 때의 동작이다. 기본값이 1장이 아니다.

C. 필드가 없다고 예약이 생략되는 것이 아니라 기본 동작은 모든 GPU 사용이다.

D. 필수 필드는 `capabilities`뿐이다. `count`나 `device_ids`는 없어도 검증을 통과하며, 실제로 `docker compose config`가 통과한다.

E. 특정 GPU를 쓰려면 `device_ids`로 직접 지정해야 한다. 지정이 없으면 0번 하나로 한정되지 않는다.

## 세트 A-04 · 배포 직후 트래픽이 끊긴다

**환경:** Kubernetes

**지문:** 사내 LLM 서빙 API(llm-serve, replicas 4)를 새 이미지로 롤링 업데이트할 때마다 클라이언트에 5xx 응답이 잠깐 나온다. 모델 적재에 100초 안팎이 걸리며, 일부 릴리스에서는 Pod가 재시작을 반복하기도 했다. 현재 Deployment는 strategy를 따로 지정하지 않았고 probe는 livenessProbe 하나만 설정돼 있다. 팀은 probe 역할과 롤아웃 동작, 롤백 절차를 정리하려 한다. 아래는 현재 Deployment 발췌와 `kubectl rollout history` 출력이다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: llm-serve}
spec:
  replicas: 4
  selector: {matchLabels: {app: llm-serve}}
  template:
    metadata: {labels: {app: llm-serve}}
    spec:
      containers:
      - name: llm
```

### A-04-1 · 롤링 업데이트 중 5xx가 나오는 이유

단일 선택 · 케이스 · 도메인 ② · L2 · 제품: Kubernetes

이 앱의 `/healthz`는 프로세스가 뜨면 곧바로 200을 돌려주고, `/ready`는 모델 적재가 끝난 뒤에만 200을 돌려준다. 롤링 업데이트 중 새 Pod가 `1/1 Running`이 되자마자 요청을 받아 5xx가 나온다. 이 문제를 해결하는 변경은 무엇인가?

A. livenessProbe의 `failureThreshold`를 3에서 20으로 올린다.

B. `/ready`를 확인하는 readinessProbe를 추가한다.

C. `strategy.type`을 `Recreate`로 바꾼다.

D. `/healthz`를 확인하는 startupProbe를 추가한다.

E. `terminationGracePeriodSeconds`를 늘린다.

**정답: B**

**상세 해설**

A. liveness 실패의 결과는 컨테이너 재시작이다. 어떤 Pod가 Service 트래픽을 받는지는 readiness가 정하므로, 임계값을 올려도 5xx는 그대로다.

B. probe를 정의하지 않은 종류는 kubelet이 항상 성공으로 간주하므로, readinessProbe가 없으면 컨테이너가 뜨는 즉시 Ready가 되어 Service 엔드포인트에 들어간다. `/ready`를 확인하는 readinessProbe를 두면 모델 적재가 끝날 때까지 Pod는 트래픽을 받지 않고, 롤링 업데이트도 새 Pod가 준비된 뒤에 다음 단계로 진행한다.

C. Recreate는 기존 Pod를 모두 먼저 종료한다. 다운타임이 오히려 커지고, 새 Pod가 준비 전에 트래픽을 받는 문제는 그대로다.

D. `/healthz`는 즉시 200이므로 startupProbe가 바로 성공한다. startupProbe는 liveness·readiness의 실행 시작 시점을 늦출 뿐이어서, readinessProbe가 없으면 Ready 판정은 달라지지 않는다.

E. 종료 시 유예 시간을 정하는 값으로 기동 직후의 트래픽 유입과는 무관하다.

**근거 문서** https://kubernetes.io/docs/concepts/workloads/pods/probes/ · 기준일 2026-10-20 · kubernetes/website main (최신 마이너 1.37) · 검증 수준: 스키마·시그니처 확인 (readinessProbe를 추가한 Deployment를 kubeconform strict로 검증)

### A-04-2 · 재시작 반복을 막는 startupProbe 값

단일 선택 · 케이스 · 도메인 ② · L2 · 제품: Kubernetes

v3 릴리스부터는 모델을 적재하는 동안 서버 포트 자체가 열리지 않고, 적재에 최대 150초가 걸린다. 그 사이 위 livenessProbe(주기 10초, 실패 허용 3회)가 컨테이너를 반복해서 죽인다. 적재가 끝난 뒤에는 지금의 liveness 설정을 그대로 유지해 교착을 빨리 감지하고 싶다. 알맞은 변경은 무엇인가?

A. livenessProbe의 `failureThreshold`를 3에서 20으로 올린다.

B. readinessProbe를 추가해 적재가 끝날 때까지 not ready로 둔다.

C. 같은 `/healthz` 검사를 하는 startupProbe를 `periodSeconds: 10`, `failureThreshold: 3`으로 추가한다.

D. 같은 `/healthz` 검사를 하는 startupProbe를 `periodSeconds: 10`, `failureThreshold: 18`로 추가한다.

E. `terminationGracePeriodSeconds`를 180으로 늘린다.

**정답: D**

**상세 해설**

A. 기동 구간은 버티지만, 기동이 끝난 뒤의 교착 감지도 200초로 느려진다. 문서가 startupProbe를 쓰라고 하는 이유가 바로 이 타협을 피하기 위해서다.

B. readiness 실패는 Pod를 Service에서 빼기만 하고 컨테이너를 재시작시키지 않는다. 그렇다고 liveness 실패가 멈추지는 않으므로 재시작 반복은 그대로다.

C. startup 예산은 `periodSeconds × failureThreshold`이다. 10 × 3 = 30초로는 150초를 감당하지 못해 startupProbe가 컨테이너를 죽인다.

D. 10 × 18 = 180초가 최악의 적재 시간 150초를 덮는다. startupProbe가 성공하기 전에는 liveness와 readiness가 실행되지 않고, 성공한 뒤에는 기존 liveness(10초 × 3)가 이어받는다.

E. 종료 시 유예 시간이어서 기동 중 liveness 실패와는 관계가 없다.

**근거 문서** https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/ · https://kubernetes.io/docs/concepts/workloads/pods/probes/ · 기준일 2026-10-20 · kubernetes/website main (최신 마이너 1.37) · 검증 수준: 스키마·시그니처 확인 (정답 구성의 Deployment를 kubeconform strict와 kubernetes Python 클라이언트 37.0.1 모델로 검증)

### A-04-3 · 이미지 태그 오타로 멈춘 롤아웃의 상태

단일 선택 · 케이스 · 도메인 ② · L3 · 제품: Kubernetes

위 Deployment(`replicas: 4`, strategy 미지정, `progressDeadlineSeconds` 미지정)에서 누군가 이미지 태그를 잘못 적어(`:v4-fnal`) 롤링 업데이트를 시작했다. 새 Pod는 모두 `ImagePullBackOff`이고 아무도 손대지 않은 채 15분이 지났다. 이때의 상태로 옳은 것은?

A. 기존 Pod 3개가 Ready로 서비스를 계속하고 새 Pod 2개가 ImagePullBackOff로 남는다. 600초가 지나면 Progressing 조건이 `ProgressDeadlineExceeded`로 바뀌지만 자동 롤백은 일어나지 않는다.

B. 새 Pod가 Ready가 되기 전에는 기존 Pod를 줄이지 않으므로 기존 Pod 4개와 새 Pod 1개가 남는다.

C. 600초가 지나면 Deployment 컨트롤러가 이전 리비전으로 자동 롤백해 기존 Pod 4개가 복구된다.

D. 600초가 지나면 컨트롤러가 롤아웃을 포기하고 새 ReplicaSet을 0으로 줄인다.

E. 기존 Pod가 모두 먼저 종료되고 새 Pod 4개가 ImagePullBackOff 상태로 남아 서비스가 완전히 중단된다.

**정답: A**

**상세 해설**

A. 기본값은 `maxUnavailable` 25%(내림)와 `maxSurge` 25%(올림)이고, 4개에서는 각각 1이다. 가용 Pod를 3개 아래로 줄일 수 없고 전체 Pod는 5개를 넘길 수 없으므로 기존 3개와 새 2개에서 멈춘다. `progressDeadlineSeconds`의 기본값 600초가 지나면 `Progressing=False, reason: ProgressDeadlineExceeded`가 보고된다. 컨트롤러는 계속 재시도할 뿐 자동으로 롤백하지 않으며, 롤백은 운영자나 상위 오케스트레이터가 한다.

B. `maxUnavailable` 허용치(1)만큼은 새 Pod가 Ready가 되기 전에도 기존 Pod를 줄일 수 있다. 기존 4개가 그대로 남지는 않는다.

C. 문서는 데드라인 초과를 상위 도구가 감지해 롤백하는 용도로 쓸 수 있다고 설명할 뿐, 컨트롤러가 스스로 롤백한다고 하지 않는다.

D. 문서는 컨트롤러가 데드라인 초과 뒤에도 Deployment를 계속 재시도한다고 설명한다. ReplicaSet을 0으로 줄이지 않는다.

E. `maxUnavailable`이 한 번에 사용 불가가 될 수 있는 Pod 수를 제한하므로, 기존 Pod가 모두 먼저 종료되는 일은 없다. 이는 `Recreate` 전략의 동작이다.

**근거 문서** https://kubernetes.io/docs/concepts/workloads/controllers/deployment/ · 기준일 2026-10-20 · kubernetes/website main (최신 마이너 1.37) · 검증 수준: 문서 대조 (기본값·라운딩·ProgressDeadlineExceeded는 원문 확인, 4/1/1 계산은 문서의 10/3/2 예시와 같은 규칙으로 도출)

### A-04-4 · 검증된 리비전으로 되돌리는 명령

단일 선택 · 케이스 · 도메인 ② · L2 · 제품: Kubernetes

현재 리비전 4가 오류율을 높이고 있다. 리비전 3에서도 같은 오류가 재현됐고, 검증을 마친 것은 리비전 2뿐이다. 위 `rollout history` 출력을 기준으로 서비스를 리비전 2의 Pod 템플릿으로 되돌리는 명령은?

A. `kubectl rollout undo deployment/llm-serve`

B. `kubectl rollout history deployment/llm-serve --revision=2`

C. `kubectl rollout restart deployment/llm-serve`

D. `kubectl rollout pause deployment/llm-serve`

E. `kubectl rollout undo deployment/llm-serve --to-revision=2`

**정답: E**

**상세 해설**

A. 인자 없는 undo는 직전 리비전, 여기서는 3으로 되돌린다. 3도 같은 오류가 있으므로 해결되지 않는다.

B. 리비전 2의 Pod 템플릿을 보여 주기만 하고 아무것도 바꾸지 않는다.

C. restart는 템플릿에 재시작 시각 어노테이션을 패치해 새 롤아웃을 일으킨다. 리비전 4의 내용이 그대로 새 Pod로 만들어질 뿐이다.

D. 롤아웃을 일시 중지하는 명령이다. 롤백이 아니며, 문서에 따르면 일시 중지된 Deployment는 resume 전에는 롤백할 수도 없다.

E. `--to-revision`으로 리비전을 지정하는 것이 문서가 안내하는 특정 리비전으로의 롤백이다. 리비전 2의 템플릿이 복원되고 롤링 업데이트로 적용된다.

## 세트 A-05 · 질문이 몰리면 확장해야 한다

**환경:** Kubernetes, KEDA

**지문:** 사내 질의응답(RAG) API인 rag-api는 업무 시작 시간에 요청이 몰려 응답이 느려진다. CPU 기준 HPA로는 반응이 늦어, KEDA ScaledObject로 바꿔 Prometheus의 요청률과 대기열 길이를 기준으로 확장하려 한다. 야간에는 비용을 줄이려 0개까지 내리는 것이 목표다. 아래는 검토 중인 ScaledObject이며 pollingInterval과 cooldownPeriod는 기본값을 명시했다. metricType은 지정하지 않았다.

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: rag-api}
spec:
  scaleTargetRef: {name: rag-api}
  pollingInterval: 30
  cooldownPeriod: 300
  minReplicaCount: 0
  maxReplicaCount: 20
  triggers:
  - type: prometheus
    name: req-rate
    metadata: {serverAddress: "http://prometheus.monitoring:9090", query: 'sum(rate(http_requests_total{app="rag-api"}[2m]))', threshold: "50"}
  - type: prometheus
    name: queue-len
    metadata: {serverAddress: "http://prometheus.monitoring:9090", query: "sum(rag_api_queue_length)", threshold: "5"}
```

### A-05-1 · 0개로 내려가는 시점

단일 선택 · 케이스 · 도메인 ② · L1 · 제품: Kubernetes

새벽 02:00에 마지막 요청이 들어온 뒤 두 지표가 모두 비활성(0)으로 보고되기 시작했다. 이 시점에 레플리카는 1개였다. 위 설정에서 `rag-api`가 0개가 되는 시점으로 가장 알맞은 것은?

A. 02:00:30 직후, 다음 폴링 때

B. 02:00 즉시

C. 02:05 전후

D. 02:10 전후

E. 0개로 내려가지 않고 1개에 머문다

**정답: C**

**상세 해설**

A. pollingInterval은 트리거를 확인하는 주기이지 0으로 내리기까지의 대기 시간이 아니다. 다음 폴링에서 비활성을 확인해도 대기는 계속된다.

B. cooldownPeriod는 마지막으로 트리거가 활성이라고 보고된 뒤 0으로 내리기 전에 기다리는 시간이다. `minReplicaCount: 0`이어도 즉시 내리지 않는다.

C. 기본값 300초(5분)가 지나야 0이 된다. 폴링이 30초 주기이므로 확인 시각이 한 주기 정도 어긋날 수 있어 "전후"로 판단한다.

D. 레플리카가 1개이므로 HPA의 1에서 N 구간 동작(스케일다운 안정화 창 등)이 끼어들지 않는다. 0과 1 사이 전환은 KEDA가 cooldownPeriod 기준으로 직접 처리한다.

E. 0과 1 사이의 전환은 HPA가 아니라 KEDA가 맡는다. `minReplicaCount: 0`이면 0까지 내려간다.

### A-05-2 · 평상시에도 2개를 유지하는 설정

단일 선택 · 케이스 · 도메인 ② · L2 · 제품: Kubernetes

콜드 스타트 지연을 피하려고 야간에도 항상 2개는 떠 있고, 부하가 오면 최대 20개까지 늘도록 바꾸려 한다. 위 ScaledObject에서 적용할 변경은?

A. `minReplicaCount`를 2로 바꾼다.

B. `minReplicaCount: 0`은 유지하고 `idleReplicaCount: 2`를 추가한다.

C. `initialCooldownPeriod: 3600`을 추가한다.

D. `cooldownPeriod`를 0으로 바꾼다.

E. `fallback`을 추가하고 `replicas: 2`로 지정한다.

**정답: A**

**상세 해설**

A. `minReplicaCount`는 KEDA가 내려갈 수 있는 최소 레플리카 수다. 2로 두면 지표가 비활성이어도 2개를 유지하고, 활성이면 HPA가 그 위로 20개까지 확장한다.

B. `idleReplicaCount`는 `minReplicaCount`보다 작아야 하고, 문서상 지원되는 값은 0뿐이다. 0보다 큰 idle 값은 올바르게 동작하지 않는다.

C. 생성 직후 일정 시간 동안 cooldown 시작을 미루는 유예일 뿐, 항상 2개를 유지하는 하한이 아니다. 시간이 지나면 0으로 내려간다.

D. cooldownPeriod는 0으로 내리기 전 대기 시간이다. 0초로 하면 비활성 즉시 0개가 되어 목적과 반대다.

E. fallback은 스케일러가 연속으로 지표를 못 가져왔을 때(`failureThreshold` 초과) 쓰는 레플리카 수다. 평상시 하한이 아니다.

### A-05-3 · 두 트리거가 있을 때의 목표 레플리카

단일 선택 · 케이스 · 도메인 ② · L3 · 제품: Kubernetes

피크 시점에 `req-rate` 쿼리 결과는 400, `queue-len` 쿼리 결과는 30이고 현재 레플리카는 6개다. HPA가 목표로 삼는 레플리카 수는? (다른 제약은 없고 위 설정을 그대로 쓴다.)

A. 6

B. 14

C. 20

D. 7

E. 8

**정답: E**

**상세 해설**

A. `queue-len` 하나만 보면 30 / 5 = 6이다. HPA는 지표별로 계산한 값 중 큰 쪽을 고르므로 작은 쪽을 택한 오류다.

B. 두 지표의 결과를 합산하는 규칙은 없다. 지표마다 따로 계산해 최댓값을 취한다.

C. 지표를 현재 레플리카에 곱하는 `Value` 유형이라면 6 × 400 / 50 = 48이 되어 `maxReplicaCount`인 20에 걸리지만, 이 설정의 metricType은 기본값 `AverageValue`다.

D. 두 값의 평균(7)을 쓰는 규칙은 없다.

E. 기본 metricType이 `AverageValue`이므로 현재 레플리카 수와 무관하게 `req-rate`는 400 / 50 = 8, `queue-len`은 30 / 5 = 6이다. 지표가 여러 개면 계산된 값 중 가장 큰 8이 선택되고 `maxReplicaCount` 20 이내다.

### A-05-4 · 축소 속도를 제한하는 위치

단일 선택 · 케이스 · 도메인 ② · L2 · 제품: Kubernetes

피크가 끝나면 레플리카가 20개에서 한꺼번에 줄어 뒤이은 소규모 요청에 지연이 생긴다. 1개 이상 구간에서 축소 속도를 분당 최대 2개로 제한하고 싶다. 알맞은 설정은?

A. `advanced.horizontalPodAutoscalerConfig.behavior.scaleUp.policies`에 `type: Pods, value: 2, periodSeconds: 60`을 둔다.

B. `advanced.horizontalPodAutoscalerConfig.behavior.scaleDown.policies`에 `type: Pods, value: 2, periodSeconds: 60`을 둔다.

C. `pollingInterval`을 60으로 늘린다.

D. `advanced.horizontalPodAutoscalerConfig.behavior.scaleDown.stabilizationWindowSeconds`를 60으로 둔다.

E. ScaledObject 최상위에 `scaleDown.policies` 필드로 `Pods: 2`를 둔다.

**정답: B**

**상세 해설**

A. scaleUp은 확장 방향의 정책이다. 축소 속도에는 영향이 없다.

B. 1에서 N 구간은 KEDA가 만든 HPA가 맡고, KEDA는 `advanced.horizontalPodAutoscalerConfig.behavior`의 값을 HPA의 `behavior` 필드로 그대로 넘긴다. HPA의 `scaleDown.policies`에서 `Pods` 유형으로 분당 최대 감소 수를 제한한다.

C. pollingInterval은 KEDA가 트리거를 확인하는 주기다. 축소되는 양의 상한과는 무관하며, 1에서 N 구간의 HPA는 자체 동기화 주기로 지표를 조회한다.

D. 안정화 창은 최근 구간의 가장 높은 권고 레플리카 수를 따라 급격한 변동을 평활화하는 장치다. 분당 제거 수의 상한이 아니고, 기본 300초에서 60초로 줄이면 오히려 축소가 빨라진다.

E. ScaledObject 최상위에 그런 필드는 없다. HPA 동작 설정은 `advanced.horizontalPodAutoscalerConfig` 아래에 둔다.

## 세트 A-06 · 배치 잡이 모델 버전을 고정해 둔다

**환경:** Databricks, Unity Catalog 모델 레지스트리, MLflow

**지문:** 물류사 '한빛'의 야간 배치 잡은 수요 예측 모델로 전 매장의 발주량을 계산한다. 모델은 Unity Catalog에 등록되어 있고, 팀은 승인된 버전을 Champion alias가 가리키게 하며 배치 코드는 alias만 읽는 방식으로 합의했다. 잡은 서비스 주체 sp-batch 권한으로 실행되고 MLflow 클라이언트는 Databricks 작업 공간에서 동작한다. 승급 스크립트를 쓴 담당자는 예전 회사에서 쓰던 작업 공간 모델 레지스트리의 습관이 남아 있다.

| --- | --- |
| 등록 모델 | main.forecast.demand\_model |
| 현재 Champion alias | 버전 3 |
| 새로 승인된 버전 | 버전 4 |
| 배치 잡 실행 주체 | sp-batch |

### A-06-1 · 승급 스크립트 고치기

단일 선택 · 케이스 · 도메인 ③ · L1 · 제품: Databricks

담당자가 작성한 승급 스크립트 초안은 아래와 같다. 이 모델은 Unity Catalog에 등록되어 있다. 버전 4를 승인 버전으로 만들려면 스크립트를 어떻게 고쳐야 하는가?

```python
client = MlflowClient()
client.transition_model_version_stage(
    "main.forecast.demand_model", "4", stage="Production")
```

A. `mlflow.set_registry_uri("databricks")`를 앞에 추가해 stage 호출을 그대로 둔다

B. `archive_existing_versions=True` 인자를 추가해 이전 버전을 보관 처리한다

C. `client.set_registered_model_alias("main.forecast.demand_model", "Champion", "4")`로 바꾼다

D. `client.set_model_version_tag(..., "stage", "Production")`으로 바꿔 태그로 승급을 표시한다

E. `mlflow.set_registry_uri("databricks-uc")`만 추가하면 stage 호출이 alias 설정으로 자동 변환된다

**정답: C**

**상세 해설**

A. "databricks"는 작업 공간(legacy) 레지스트리를 가리킨다. 문서는 Unity Catalog가 켜진 작업 공간에서는 그 절차를 쓰지 말라고 안내하므로, UC에 등록된 3단계 이름 모델의 승급 방법이 될 수 없다.

B. `archive_existing_versions`는 stage 호출의 옵션일 뿐이라 같은 stage API를 계속 쓰는 것이다. 문서는 Unity Catalog 모델에서 stage가 지원되지 않는다고 명시한다.

C. 문서는 Unity Catalog 모델의 승급 수단으로 3단계 이름과 alias를 안내하고 `set_registered_model_alias`로 alias를 지정하는 예를 든다. Champion을 버전 4로 옮기면 alias만 읽는 배치 코드는 그대로 새 버전을 쓴다.

D. 태그는 메타데이터일 뿐이고 alias 해석에 영향을 주지 않는다. 배치가 읽는 Champion alias는 여전히 버전 3을 가리킨다.

E. 레지스트리 URI를 바꿔도 stage 호출이 alias 호출로 변환되지 않는다. Unity Catalog 모델에는 stage 개념 자체가 없다.

### A-06-2 · 로딩 시 권한 오류

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Databricks

sp-batch에는 아래 권한만 부여되어 있다. 그런데 배치 잡이 Champion alias로 모델을 불러오는 순간 권한 오류로 실패한다. 모델을 불러오기 위해 추가로 필요한 최소 권한은 무엇인가?

```sql
GRANT USE CATALOG ON CATALOG main          TO `sp-batch`;
GRANT USE SCHEMA  ON SCHEMA  main.forecast TO `sp-batch`;
GRANT SELECT      ON SCHEMA  main.forecast TO `sp-batch`;
```

A. 등록 모델 main.forecast.demand\_model에 대한 EXECUTE

B. 등록 모델 main.forecast.demand\_model에 대한 MANAGE

C. main.forecast 스키마에 대한 CREATE MODEL

D. main 카탈로그에 대한 USE CATALOG를 다시 부여

E. main 카탈로그 수준의 SELECT

**정답: A**

**상세 해설**

A. 문서는 alias로 모델을 불러올 때 등록 모델에 대한 EXECUTE와 함께 그 모델이 속한 카탈로그와 스키마의 USE CATALOG·USE SCHEMA가 필요하다고 한다. 나머지 둘은 이미 부여되어 있으므로 EXECUTE만 빠져 있다.

B. MANAGE는 모델을 관리하는 상위 권한이다. 문서가 로딩에 요구하는 것은 EXECUTE이므로 과도한 부여이고 최소 권한 원칙에도 어긋난다.

C. CREATE MODEL은 스키마에 새 모델을 등록할 때 필요한 권한이다. 이미 등록된 모델을 불러오는 데는 쓰이지 않는다.

D. USE CATALOG는 첫 줄에서 이미 부여되었다. 다시 부여해도 달라지는 것이 없다.

E. SELECT는 테이블 데이터를 읽는 권한이고 스키마에 이미 부여되어 있다. 모델 로딩 요건으로 문서에 나오는 것은 EXECUTE다.

### A-06-3 · alias는 어느 버전을 가리키는가

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Databricks

모델 레지스트리의 작업 이력이 아래와 같다. 이력 6의 배치 잡은 Champion alias로 모델을 불러온다. 이력 6 시점에 배치가 쓰는 버전과, 이 시점에 버전 2에 붙어 있는 alias 상태로 옳은 것은?

| 번호 | 작업 |
| --- | --- |
| 1 | 버전 1, 2, 3을 순서대로 등록 |
| 2 | Champion alias를 버전 2로 지정 |
| 3 | Challenger alias를 버전 3으로 지정 |
| 4 | 새 모델 버전 4를 등록 |
| 5 | Champion alias를 버전 3으로 지정 |
| 6 | 배치 잡이 Champion alias로 모델 로딩 |

A. 버전 4를 쓴다. 가장 최근에 등록한 버전이 자동으로 Champion이 되고 버전 2에는 alias가 없다

B. 버전 3을 쓴다. 버전 2에는 Champion이 그대로 남아 두 버전이 같은 alias를 공유한다

C. 버전 2를 쓴다. 이력 5는 Champion이 이미 지정된 모델에는 적용되지 않는다

D. 버전 3을 쓴다. Champion을 옮기면서 Challenger alias도 함께 제거되어 버전 3에는 Champion만 남는다

E. 버전 3을 쓴다. 버전 2에는 alias가 없고 버전 3에는 Champion과 Challenger가 모두 붙어 있다

**정답: E**

**상세 해설**

A. 새 버전을 등록해도 alias는 자동으로 옮겨 가지 않는다. 로컬 레지스트리에서 실행해 보면 버전을 더 등록한 뒤에도 Champion은 직전에 지정한 버전에 그대로 있다.

B. 한 alias는 한 모델 안에서 한 버전만 가리킨다. 문서는 alias를 특정 버전을 가리키는 변경 가능한 이름 참조라고 설명하고, 다시 지정하면 이전 버전에서 떨어진다.

C. 문서는 alias를 mutable하다고 설명한다. 이미 지정된 alias도 같은 호출로 다른 버전으로 옮길 수 있다.

D. alias는 이름마다 독립이다. Champion을 옮겨도 Challenger는 건드리지 않는다.

E. Champion이 버전 2에서 3으로 옮겨지면서 버전 2는 alias를 잃고, 버전 3에는 먼저 붙어 있던 Challenger와 새로 붙은 Champion이 함께 남는다. 배치는 Champion이 가리키는 버전 3을 쓴다.

### A-06-4 · 개발과 운영 환경 나누기

단일 선택 · 케이스 · 도메인 ③ · L3 · 제품: Databricks

한빛은 같은 Unity Catalog 메타스토어에 연결된 개발 작업 공간과 운영 작업 공간을 둔다. 요구사항은 세 가지다. 첫째, 두 작업 공간이 같은 모델 레지스트리를 공유한다. 둘째, 개발자는 운영 모델의 승급을 직접 바꿀 수 없다. 셋째, 승인 버전을 바꿀 때 배치 코드를 재배포하지 않는다. 이 요구를 모두 만족하는 구성은?

A. 작업 공간마다 Workspace Model Registry에 모델을 두고 Staging·Production 스테이지로 환경을 나눈다

B. dev와 prod 카탈로그를 따로 두고 각각에 같은 이름 체계의 모델을 등록한다. 운영 카탈로그의 모델은 승급 담당 그룹에만 쓰기 권한을 주고 배치는 각 환경 모델의 Champion alias를 읽는다

C. 카탈로그 하나에 모델 하나만 두고 Champion-dev, Champion-prod 같은 alias 이름으로 환경을 나눈다

D. 운영 배치가 dev 카탈로그의 모델 Champion alias를 직접 읽게 하고, 개발자가 검증이 끝나면 alias를 옮긴다

E. 환경별 설정 파일에 모델 버전 번호를 적어 두고 승인할 때마다 설정 파일을 배포한다

**정답: B**

**상세 해설**

A. 문서는 Unity Catalog가 켜진 작업 공간에서는 Workspace Model Registry(legacy) 절차를 쓰지 말라고 안내하고, 작업 공간 간 모델 공유에는 Unity Catalog 모델을 권장한다. 작업 공간별 레지스트리는 첫째 요구도 만족하지 못한다.

B. 문서는 3단계 이름 체계로 모델의 환경을 나타내고 승급에는 alias를 쓰라고 안내한다. 카탈로그를 환경 경계로 삼으면 권한을 카탈로그와 모델 단위로 나눌 수 있어 둘째 요구를 만족하고, alias를 옮기는 것만으로 승급되므로 셋째 요구도 만족한다. 메타스토어를 공유하므로 첫째 요구도 충족한다.

C. 권한은 카탈로그, 스키마, 모델 같은 대상에 부여하지 alias 이름에는 부여하지 않는다. 모델이 하나뿐이면 환경별 권한 경계를 만들 수 없어 둘째 요구가 깨진다.

D. 운영 입력이 개발 카탈로그의 모델에 의존하게 되어 개발자가 옮기는 alias 하나가 곧 운영 승급이 된다. 둘째 요구를 위반한다.

E. 승인 버전을 바꿀 때마다 설정 파일을 배포해야 하므로 셋째 요구를 만족하지 못한다. 승인 지점이 레지스트리 밖으로 나가는 문제도 있다.

B. Foundation Model APIs의 provisioned throughput 엔드포인트

C. Databricks 밖에서 호스팅되는 모델을 연결하는 external model 엔드포인트

D. 커스텀 모델(custom model) 서빙 엔드포인트

E. AI Search(구 Vector Search) 엔드포인트

**정답: D**

**상세 해설**

A. pay-per-token은 Databricks가 호스팅하는 기반 모델을 바로 쓰는 방식이다. 자체 학습해 패키징한 모델을 올리는 유형이 아니다.

B. provisioned throughput은 기반 모델과 그 파인튜닝 변형을 성능 보장과 함께 배포하는 방식이다. 자체 학습한 분류 모델의 서빙 유형이 아니다.

C. external model은 Databricks 밖에 호스팅된 파운데이션 모델을 연결하는 용도다. 이 모델은 Unity Catalog에 등록되어 있다.

D. 문서는 모델 서빙이 다루는 대상으로 MLflow 형식으로 패키징된 Python 모델, 즉 커스텀 모델을 든다. 사기 탐지 모델이 여기에 해당한다.

E. AI Search는 벡터 인덱스를 제공하는 서비스이고 모델 추론 서빙용 엔드포인트가 아니다.

### A-07-2 · 파인튜닝 변형의 운영 배포

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Databricks

사내 데이터로 파인튜닝한 기반 모델 변형을 운영에 올려야 하고 처리량과 성능 보장이 필요하다. Foundation Model APIs의 어떤 방식을 골라야 하는가?

A. pay-per-token. 즉시 쓸 수 있고 호출한 만큼만 낸다

B. provisioned throughput

C. external model 엔드포인트로 파인튜닝 변형을 연결

D. pay-per-token 엔드포인트에 파인튜닝 가중치를 업로드

E. 커스텀 모델 서빙 엔드포인트의 GPU\_MEDIUM 워크로드

**정답: B**

**상세 해설**

A. 문서는 pay-per-token을 가장 쉽게 시작하는, 즉시 쓸 수 있는 방식으로 소개한다. 성능 보장과 파인튜닝 변형을 연결해 설명하는 쪽은 provisioned throughput이다.

B. 문서는 성능 보장, 파인튜닝 모델이 필요한 워크로드에 provisioned throughput을 안내하고 기반 모델의 파인튜닝 변형을 지원한다고 적는다. 모든 운영 워크로드에 권장한다고도 한다.

C. external model은 Databricks 밖에서 호스팅되는 모델용이다. Databricks에서 파인튜닝한 변형을 올리는 방법이 아니다.

D. pay-per-token 엔드포인트에 사용자 가중치를 올리는 기능은 문서에 없다. 파인튜닝 변형은 provisioned throughput으로 배포한다.

E. 커스텀 모델 엔드포인트는 MLflow 패키지 모델용이다. 문서가 파인튜닝 변형과 성능 보장을 묶어 안내하는 경로는 provisioned throughput이다.

### A-07-3 · 한밤 뒤 첫 요청이 느리다

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Databricks

운영 중인 사기 탐지 엔드포인트의 설정과 지연 기록이 아래와 같다. 새벽 첫 요청의 지연이 크게 튄다. 원인과 조치로 옳은 것은?

```json
{
  "name": "fraud-scoring",
  "served_entities": [{
    "entity_name": "main.risk.fraud_model",
    "entity_version": "7",
    "workload_type": "CPU",
    "workload_size": "Small",
    "scale_to_zero_enabled": true
  }]
}
```

| 구간 | 요청/분 | p99 지연 |
| --- | --- | --- |
| 14:00 | 120 | 85 ms |
| 03:00\~04:30 | 0 | 없음 |
| 04:31 (첫 요청) | 1 | 38 s |

A. 유휴 동안 용량이 0으로 줄었다가 첫 요청에서 cold start가 발생한다. 운영 엔드포인트는 scale\_to\_zero\_enabled를 false로 두고 최소 용량을 유지한다

B. 모델 크기 때문이다. workload\_size를 Large로 올리면 첫 요청 지연이 사라진다

C. 요청이 몰려 큐가 찼다. max\_provisioned\_concurrency를 올린다

D. CPU에서 처리하기 때문이다. workload\_type을 GPU\_SMALL로 바꾸면 cold start가 사라진다

E. scale-to-zero는 운영 권장 설정이므로 클라이언트 타임아웃만 늘린다

**정답: A**

**상세 해설**

A. 문서는 엔드포인트가 0으로 줄었다가 늘어날 때 cold start 지연이 생긴다고 설명하고, 0일 때는 용량이 보장되지 않으므로 운영 엔드포인트에는 scale to zero를 권장하지 않는다고 적는다. 지연이 요청이 끊긴 뒤 첫 요청에서만 생긴 것이 증거다.

B. 지연은 부하가 높은 14:00이 아니라 유휴 뒤 첫 요청에서만 튄다. 인스턴스 크기를 올려도 용량이 0으로 줄었다 돌아오는 현상은 남는다.

C. 03:00\~04:30의 요청은 0이었으므로 큐가 찼을 가능성이 없다. 최대 동시성을 올릴 이유가 없다.

D. 유휴 시 용량이 0이 되는 문제는 컴퓨트 종류와 무관하다. GPU로 바꾸면 비용만 늘고 scale to zero의 cold start는 그대로다.

E. 문서는 scale to zero를 운영에 권장하지 않는다고 명시한다. 타임아웃을 늘리면 증상만 가리고 용량 미보장은 남는다.

### A-07-4 · GPU 엔드포인트의 레플리카 수

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Databricks

사기 탐지 엔드포인트를 GPU로 옮기며 아래처럼 설정했다. 문서의 규칙에 따르면 유휴 시 최소 레플리카 수와 피크 시 최대 레플리카 수는 각각 얼마인가?

```json
{
  "workload_type": "GPU_SMALL",
  "scale_to_zero_enabled": false,
  "min_provisioned_concurrency": 8,
  "max_provisioned_concurrency": 20
}
```

A. 최소 8개, 최대 20개

B. 최소 1개, 최대 5개

C. 최소 2개, 최대 5개

D. 최소 4개, 최대 10개

E. 최소 0개, 최대 5개

**정답: C**

**상세 해설**

A. 동시성 값을 레플리카 수로 그대로 읽은 것이다. 문서는 GPU 엔드포인트에서 레플리카 수가 동시성 값을 4로 나눈 값이라고 한다.

B. 최대는 20÷4=5로 맞지만 최소가 틀렸다. 8÷4=2이므로 최소는 2개다.

C. GPU 엔드포인트의 레플리카 수는 동시성 ÷ 4다. 최소 8÷4=2개, 최대 20÷4=5개이며, 문서의 예(12 → 3 레플리카)와 같은 계산이다.

D. 2로 나눈 값이다. 문서의 나누는 수는 4다.

E. scale\_to\_zero\_enabled가 false이므로 최소가 0이 될 수 없다. 최소 동시성 8도 최소 2개 레플리카로 이어진다.

## 세트 A-08 · AI 함수 이름 변경과 권한

**환경:** Snowflake

**지문:** 데이터팀은 SNOWFLAKE.CORTEX 스키마의 함수로 만든 야간 티켓 분류 파이프라인을 AI\_ 접두 함수로 옮기는 중이다. 보안 담당자는 신규 분석 롤에 따로 권한을 줘야 하는지, 기존 함수를 언제까지 쓸 수 있는지 확인해 달라고 요청했다. 팀은 마이그레이션 문서를 기준으로 호출부를 고치려 하며, 아래는 현재 운영 중인 쿼리다.

```sql
SELECT SNOWFLAKE.CORTEX.CLASSIFY_TEXT(body, ['환불','배송','기타']):label::STRING AS category,
       SNOWFLAKE.CORTEX.COMPLETE('llama3.1-70b', '요약: ' || body) AS summary
FROM support.tickets;
```

### A-08-1 · 마이그레이션 문서와 일치하는 판단

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Snowflake

SNOWFLAKE.CORTEX 함수를 AI\_ 함수로 옮기는 계획을 세우고 있다. Snowflake의 마이그레이션 문서 내용과 일치하는 판단은 무엇인가?

A. 이전 함수는 폐기 예정으로 공지되어 있으므로 종료일 전에 모든 호출을 한꺼번에 교체해야 한다.

B. EMBED\_TEXT\_768과 EMBED\_TEXT\_1024는 각각 AI\_EMBED\_768, AI\_EMBED\_1024로 대응된다.

C. EXTRACT\_ANSWER는 AI\_EXTRACT로 대응되며 인자와 출력이 달라지므로 호출부를 고쳐야 한다. 문서는 이전 함수의 폐기나 종료일을 명시하지 않으므로 단계적으로 옮길 수 있다.

D. SENTIMENT는 AI\_SENTIMENT로 대응되며 기존처럼 FLOAT 값을 그대로 반환한다.

E. TRY\_COMPLETE는 별도의 AI\_TRY\_COMPLETE로 대응된다.

**정답: C**

**상세 해설**

A. 마이그레이션 문서는 이전 함수의 폐기나 종료일을 밝히지 않는다. 폐기 예정이라는 전제가 문서에 없다.

B. 두 함수는 하나의 AI\_EMBED로 합쳐진다. 차원별 이름은 만들어지지 않는다.

C. 문서의 대응표는 EXTRACT\_ANSWER를 AI\_EXTRACT로 매핑하고 인자와 출력이 바뀌는 변경으로 분류한다. 폐기를 명시하지 않으므로 순차 이행이 가능하다.

D. AI\_SENTIMENT는 출력 형식이 바뀌어 FLOAT가 아니라 OBJECT를 반환한다.

E. TRY\_COMPLETE는 AI\_COMPLETE로 대응되고 오류 처리 방식이 달라진다. AI\_TRY\_COMPLETE라는 별도 함수는 대응표에 없다.

### A-08-2 · 분류 결과 파싱 수정

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Snowflake

운영 쿼리의 첫 열을 `AI_CLASSIFY(body, ['환불','배송','기타'])`로 바꾸려 한다. 기존 코드는 `:label::STRING`으로 카테고리를 꺼냈다. 카테고리 문자열을 얻으려면 파싱을 어떻게 고쳐야 하는가?

A. `AI_CLASSIFY(...):labels[0]::STRING`으로 고친다. 결과가 `{"labels":[...]}` 형태이므로 배열의 첫 요소를 꺼낸다.

B. 반환 형태가 같으므로 `:label::STRING`을 그대로 둔다.

C. 반환값이 이미 VARCHAR이므로 `::STRING` 캐스트만 남기고 경로 표현을 제거한다.

D. `AI_CLASSIFY(...):response:label::STRING`으로 고친다. 결과가 error와 response를 가진 객체다.

E. `AI_CLASSIFY(...):value::STRING`으로 고친다. 결과가 value와 error를 가진 객체다.

**정답: A**

**상세 해설**

A. AI\_CLASSIFY는 `labels` 배열을 가진 객체를 반환한다. 단일 레이블 모드에서는 요소가 하나이므로 `:labels[0]`로 꺼낸다.

B. 반환 형태가 바뀌었다. 문서는 CLASSIFY\_TEXT에서 AI\_CLASSIFY로 옮길 때 출력 형식이 달라지는 변경으로 분류한다.

C. 반환은 문자열이 아니라 직렬화된 객체이므로 경로 표현 없이 캐스트만으로는 레이블을 꺼낼 수 없다.

D. error와 response 구조는 AI\_EXTRACT의 반환 형태다. AI\_CLASSIFY에는 response 래퍼가 없다.

E. value와 error 객체는 return\_error\_details를 TRUE로 줄 때의 형태다. 기본 호출에는 value 래퍼가 없다.

### A-08-3 · 신규 롤의 기본 권한

단일 선택 · 케이스 · 도메인 ③ · L1 · 제품: Snowflake

신규로 만든 분석 롤 `ANALYST_R`에는 Cortex 관련 GRANT를 하나도 하지 않았다. 이 롤로 `AI_CLASSIFY`를 호출해 보니 권한 오류 없이 동작했다. 기본 설정에서 이것이 가능한 이유는 무엇인가?

A. 호출 주체가 ACCOUNTADMIN 계열이 아니어도 모든 롤이 AI 함수를 소유자 권한으로 호출하기 때문이다.

B. AI\_FUNCTIONS\_USER 데이터베이스 롤이 기본적으로 PUBLIC에 부여되어 있기 때문이다.

C. AI 함수가 SYSADMIN 소유의 함수로 만들어져 있어 호출자 롤을 검사하지 않기 때문이다.

D. CORTEX\_ENABLED\_CROSS\_REGION 기본값이 ANY\_REGION이라 롤과 관계없이 호출이 허용되기 때문이다.

E. USE AI FUNCTIONS 권한과 CORTEX\_USER 데이터베이스 롤이 기본적으로 PUBLIC에 부여되어 있고, 모든 롤은 PUBLIC을 상속하기 때문이다.

**정답: E**

**상세 해설**

A. AI 함수 호출에는 계정 수준 권한과 데이터베이스 롤이 필요하다. 소유자 권한 호출이라는 설명은 문서에 없다.

B. AI\_FUNCTIONS\_USER는 기본으로 PUBLIC에 부여되지 않는다. 문서는 이를 명시한다.

C. 호출자 롤을 검사하지 않는다는 전제가 틀렸다. USE AI FUNCTIONS와 데이터베이스 롤 둘 다 필요하다.

D. 이 파라미터는 모델이 다른 리전에서 추론되도록 허용하는 설정이다. 호출 권한과는 무관하다.

E. 문서는 USE AI FUNCTIONS 권한과 CORTEX\_USER 롤이 기본으로 PUBLIC에 부여된다고 밝힌다. 따라서 별도 GRANT 없이도 호출된다.

### A-08-4 · 응답과 토큰 사용량을 함께 받기

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Snowflake

요약 열의 `COMPLETE`를 `AI_COMPLETE`로 옮긴 뒤, 요약 문자열과 함께 토큰 사용량(usage)도 같은 호출 결과로 받아 관측 테이블에 적재하려 한다. 어떻게 해야 하는가?

A. 인자를 바꾸지 않아도 기본 `AI_COMPLETE(model, prompt)` 결과가 usage를 포함한 OBJECT다.

B. `AI_COMPLETE(model => ..., prompt => ..., show_details => TRUE)`로 호출한다. 결과는 choices, created, model, usage를 가진 JSON 객체다.

C. response\_format만 지정한다. 구조화 출력 객체에 usage 필드가 자동으로 붙는다.

D. model\_parameters에 `{'usage': TRUE}`를 넣는다.

E. 호출 뒤에 `AI_COUNT_TOKENS`를 붙이면 같은 결과 객체에 응답 토큰 수가 병합된다.

**정답: B**

**상세 해설**

A. show\_details와 response\_format을 지정하지 않은 기본 호출은 응답 문자열을 반환한다.

B. show\_details를 TRUE로 주면 choices, created, model, usage를 가진 JSON 객체를 반환한다. 위치 인자로는 앞선 선택 인자를 채워야 하므로 이름 인자로 지정한다.

C. response\_format만 지정하면 그 형식을 따르는 객체가 반환된다. usage는 show\_details를 TRUE로 줄 때 함께 온다.

D. 그런 model\_parameters 키는 문서에 없다. usage는 show\_details로 받는다.

E. AI\_COUNT\_TOKENS는 별도의 계산 함수다. AI\_COMPLETE 결과에 값이 병합되지 않는다.

## 세트 A-09 · RAG 검색 결과가 오래됐다

**환경:** Snowflake

**지문:** 사내 규정 챗봇은 Cortex Search 서비스에서 문서 조각을 찾아 답한다. 규정 원본 테이블은 매 시간 갱신되는데, 담당자가 규정을 고친 뒤에도 챗봇이 하루 가까이 이전 내용을 답한다는 신고가 접수됐다. 서비스는 아래 정의로 만들어져 있다. 운영팀은 서비스 설정, 생성 옵션, 호출 방식, 권한을 차례로 점검하려 한다.

```sql
CREATE CORTEX SEARCH SERVICE kb_search
  ON chunk_text
  ATTRIBUTES dept, doc_url
  WAREHOUSE = kb_wh
  TARGET_LAG = '1 day'
AS (SELECT chunk_text, dept, doc_url FROM kb.docs.chunks);
```

### A-09-1 · 반영 지연의 원인 설정

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Snowflake

원본 테이블은 매 시간 갱신되는데 검색 결과는 하루 가까이 낡아 있다. 이 정의에서 반영 지연의 상한을 정하는 설정은 무엇이며, 어떻게 고쳐야 하는가?

A. ON 절의 검색 컬럼을 `doc_url`로 바꾼다.

B. ATTRIBUTES에 갱신 시각 컬럼을 추가한다.

C. 질의의 limit을 1000으로 늘린다.

D. TARGET\_LAG를 필요한 최신성에 맞게 더 짧은 값으로 줄인다.

E. REFRESH\_MODE를 FULL로 지정해 매번 전체를 다시 계산하게 한다.

**정답: D**

**상세 해설**

A. ON은 검색 대상 텍스트 컬럼을 정한다. 갱신 주기와는 관계가 없다.

B. ATTRIBUTES는 필터링에 쓸 컬럼 목록이다. 컬럼을 더해도 서비스가 갱신되는 시점은 바뀌지 않는다.

C. limit은 질의 한 번에 돌려줄 결과 수다. 인덱스가 얼마나 최신인지와 무관하다.

D. TARGET\_LAG는 서비스 내용이 원본 테이블 변경에 뒤처질 수 있는 최대 시간이다. 1 day를 줄이면 반영이 빨라진다.

E. FULL은 변경마다 임베딩 전체를 다시 계산하는 모드다. 문서는 증분 갱신이 지원되지 않을 때에만 권장한다. 지연 상한을 정하는 설정도 아니다.

### A-09-2 · 생성 직후 질의가 실패하는 이유

단일 선택 · 케이스 · 도메인 ③ · L2 · 제품: Snowflake

다른 환경에 같은 정의에 `INITIALIZE = ON_SCHEDULE`만 추가해 서비스를 만들었더니, 생성 직후 첫 질의가 실패하거나 결과가 비어 있었다. 지금 바로 질의가 가능한 상태로 만들려면 어떻게 해야 하는가?

A. `ALTER CORTEX SEARCH SERVICE ... SET INITIALIZE = ON_CREATE`로 바꾼다.

B. `INITIALIZE = ON_CREATE`(기본값)로 `CREATE OR REPLACE`를 실행해 서비스를 다시 만든다.

C. TARGET\_LAG를 더 길게 늘려 다음 갱신까지 여유를 둔다.

D. 질의의 limit을 낮춰 첫 질의의 부하를 줄인다.

E. 서비스 생성자 롤에 CORTEX\_USER를 추가로 부여한다.

**정답: B**

**상세 해설**

A. INITIALIZE는 생성 뒤에 변경할 수 없는 속성이다.

B. ON\_CREATE는 생성 시점에 동기 갱신을 수행한다. ON\_SCHEDULE는 다음 예약 갱신 때까지 데이터가 채워지지 않아 질의가 실패할 수 있다. 변경이 안 되므로 CREATE OR REPLACE로 다시 만든다.

C. 지연 목표를 늘리면 첫 갱신이 더 늦어질 뿐이다. 데이터를 즉시 채우지 못한다.

D. limit은 결과 개수 제한이다. 인덱스가 비어 있는 원인을 바꾸지 못한다.

E. 생성자 권한은 서비스를 만들 때 필요한 것이다. 이미 만들어진 서비스의 초기 데이터 적재와 무관하다.

### A-09-3 · 운영 앱에서 서비스 호출하기

단일 선택 · 케이스 · 도메인 ③ · L1 · 제품: Snowflake

챗봇 백엔드가 `RAG_DB.DOCS` 스키마의 `kb_search` 서비스를 호출해 `dept`가 `HR`인 문서 조각을 5건 가져와야 한다. `chunk_text`와 `doc_url`을 반환받는다. 다음 중 서비스 호출로 올바른 것은 무엇인가?

A. 백엔드 SQL에서 `SNOWFLAKE.CORTEX.SEARCH_PREVIEW`를 호출해 결과를 파싱한다.

B. REST 경로 `.../cortex-search-services/kb_search:query`에 limit을 2000으로 지정해 요청한다.

C. `/api/v2/databases/RAG_DB/schemas/DOCS/cortex-search-services/kb_search:query`로 본문 `{"query": "...", "columns": ["chunk_text","doc_url"], "filter": {"@eq": {"dept": "HR"}}, "limit": 5}`를 보낸다.

D. REST 본문의 filter에서 `{"@eq": {"chunk_text": "연차"}}`로 검색 컬럼 값을 일치시킨다.

E. `GET /api/v2/cortex/search/kb_search?q=...` 형태로 호출한다.

**정답: C**

**상세 해설**

A. SEARCH\_PREVIEW는 서비스를 검증하는 용도다. 문서는 최종 사용자 애플리케이션의 검색 질의 제공용이 아니라고 하며, 문자열 리터럴만 받고 응답이 300 KB로 제한되고 REST·Python보다 지연이 길다.

B. limit의 최댓값은 1000이다. 2000은 허용 범위를 넘는다.

C. 문서의 REST 경로 형식과 본문 필드(query, columns, filter, limit)를 따른다. dept는 ATTRIBUTES에 있으므로 @eq 필터가 가능하고 limit 5는 범위 안이다.

D. 필터는 ATTRIBUTES에 정의한 컬럼에만 적용된다. chunk\_text는 ON 컬럼이지 ATTRIBUTES가 아니다.

E. 문서화된 경로가 아니다. 서비스 호출 경로는 데이터베이스·스키마·서비스 이름을 포함한 :query 형식이다.

### A-09-4 · 갱신 주기, 필터, 접근 권한을 함께 만족하는 설계

단일 선택 · 케이스 · 도메인 ③ · L3 · 제품: Snowflake

신규 서비스 `hr_search`를 설계한다. 요구사항은 세 가지다. 첫째, 원본 변경이 15분 안에 반영되어야 한다. 둘째, `region` 값으로 결과를 필터링해야 한다. 셋째, 지원팀 롤 `SUPPORT_R`은 원본 테이블 `hr.docs.chunks`에 SELECT 권한 없이 검색만 해야 한다. 원본 테이블의 DATA\_RETENTION\_TIME\_IN\_DAYS는 1이다. 요구사항을 모두 만족하는 구성은 무엇인가?

A. `ON chunk_text ATTRIBUTES region WAREHOUSE = hr_wh TARGET_LAG = '15 minutes'`로 만들고, `SUPPORT_R`에 서비스와 그 데이터베이스·스키마의 USAGE를 부여한다. 원본 테이블 SELECT는 주지 않는다.

B. `TARGET_LAG = '2 days'`로 만들고, 15분 요구는 질의 시점 캐시 설정으로 맞춘다.

C. ATTRIBUTES를 생략하고 질의 시 `region` 필터를 조건으로 붙인다.

D. `TARGET_LAG = '15 minutes'`로 만들고, 검색은 호출자 권한으로 실행되므로 `SUPPORT_R`에 원본 테이블 SELECT도 반드시 부여한다.

E. `ON region`으로 만들어 필터와 검색을 한 컬럼으로 처리하고 `TARGET_LAG = '15 minutes'`를 쓴다.

**정답: A**

**상세 해설**

A. 15분은 원본의 보존 기간(1일)보다 짧다. region은 ATTRIBUTES에 두어야 필터에 쓸 수 있다. 서비스는 소유자 권한으로 검색하므로 질의 롤은 서비스와 상위 데이터베이스·스키마의 USAGE만 있으면 된다.

B. 2일은 원본 보존 기간(1일)보다 길어 문서의 권고(보존 기간보다 짧게)에 어긋나고 15분 요구도 못 맞춘다. 질의 시점 캐시 설정이라는 수단도 문서에 없다.

C. 필터는 ATTRIBUTES에 정의한 컬럼에만 적용되므로 ATTRIBUTES를 생략하면 region 필터를 쓸 수 없다.

D. Cortex Search 서비스는 소유자 권한으로 검색을 수행한다. 질의 롤에 원본 SELECT가 필요하다는 전제가 틀렸고, 불필요하게 원본 접근까지 열게 된다.

E. ON은 검색할 텍스트 컬럼이다. 필터용 컬럼은 ATTRIBUTES로 따로 정의하며, 본문 검색 컬럼이 사라지면 검색 품질 자체가 무너진다.

### A-10-1 · Agent 없는 환경의 전송 설정

단일 선택 · 케이스 · 도메인 ④ · L2 · 제품: Datadog

컨테이너는 아래 환경 변수와 시작 명령으로 실행된다. 코드에서 `LLMObs.enable`은 호출하지 않는다. Agent가 없는 이 환경에서 데이터가 Datadog으로 직접 전송되려면 무엇을 추가해야 하는가?

```
DD_SITE=datadoghq.com
DD_LLMOBS_ENABLED=1
DD_LLMOBS_ML_APP=support-bot
CMD ["ddtrace-run", "uvicorn", "app.main:app"]
```

A. `DD_API_KEY`만 추가한다.

B. `DD_LLMOBS_AGENTLESS_ENABLED=1`만 추가한다.

C. `DD_LLMOBS_AGENTLESS_ENABLED=1`과 `DD_API_KEY`를 함께 추가한다.

D. `DD_LLMOBS_SAMPLE_RATE=1.0`을 추가한다.

E. 다른 노드의 Agent 주소를 `DD_AGENT_HOST`로 지정한다.

A. API 키만으로는 부족하다. `DD_LLMOBS_AGENTLESS_ENABLED`의 기본값이 false라서 SDK는 여전히 Agent를 거치는 경로를 쓴다.

C. 문서는 Agent를 쓰지 않을 때 `DD_LLMOBS_AGENTLESS_ENABLED`를 1이나 true로 두라고 하고, agentless 전송에는 `DD_API_KEY`가 필요하다. 둘 다 있어야 직접 전송된다.

D. 샘플링 비율은 기본값이 이미 1.0이고 전송 경로와 무관하다.

E. 지문에서 이 클러스터에는 Agent가 없다고 했다. 가리킬 Agent가 없으므로 주소를 지정해도 소용이 없다.

### A-10-2 · ddtrace-run과 코드 활성화의 병행

단일 선택 · 케이스 · 도메인 ④ · L1 · 제품: Datadog

시작 명령과 애플리케이션 코드가 아래와 같다. 설정 방식 측면에서 올바른 조치는 무엇인가?

```
CMD ["ddtrace-run", "uvicorn", "app.main:app"]

# app/main.py
LLMObs.enable(ml_app="support-bot", agentless_enabled=True,
              site="datadoghq.com", api_key=os.environ["DD_API_KEY"])
```

A. 둘 중 한 방식만 쓴다. `ddtrace-run`을 유지하려면 코드의 `LLMObs.enable`을 없애고 환경 변수로 설정한다.

B. `LLMObs.enable` 호출을 `app/main.py`의 첫 줄로 옮겨 `ddtrace-run`보다 먼저 실행되게 한다.

C. `LLMObs.enable(integrations_enabled=False)`를 지정해 `ddtrace-run`과 충돌하지 않게 한다.

D. `DD_LLMOBS_ENABLED=0`을 지정한 채 두 방식을 모두 남긴다.

E. `DD_API_KEY`를 환경 변수로도 한 번 더 지정한다.

**정답: A**

**상세 해설**

A. 문서는 코드 방식(`LLMObs.enable`)을 `ddtrace-run` 명령과 함께 쓰지 말라고 안내한다. 하나만 고르면 된다.

B. 호출 위치의 문제가 아니다. 두 방식을 같이 쓰는 것 자체가 문서가 쓰지 말라고 한 구성이다.

C. `integrations_enabled`는 자동 통합을 켜고 끄는 옵션이다. 두 방식 병행 금지를 풀어 주지 않고, `ddtrace-run`은 통합을 자동으로 모두 켠다.

D. 환경 변수 방식 자체를 꺼 버려 `ddtrace-run` 방식의 의미가 사라지고, 두 방식 병행을 허용하는 방법도 아니다.

E. 키를 어디에 지정하느냐는 병행 금지와 관련이 없다.

### A-10-3 · 루트가 될 수 없는 span 종류

단일 선택 · 케이스 · 도메인 ④ · L2 · 제품: Datadog

요청 진입점 함수가 아래처럼 정의되어 있다. 이 함수가 트레이스의 루트 span이 되도록 데코레이터를 바꾸려 한다. 문서가 루트가 될 수 있다고 하는 종류로 바꾸는 것은 어느 것인가?

```python
@retrieval(name="handle_request")
def handle(question):
    docs = search_docs(question)      # 벡터 DB 조회
    return generate(question, docs)   # LLM 호출
```

A. `@task`

B. `@tool`

C. `@embedding(model_name="text-embed")`

D. `@retrieval(name="handle_request", session_id=sid)`로 세션 ID만 추가한다.

E. `@workflow`

**정답: E**

**상세 해설**

A. task는 외부 서비스 호출이 없는 독립 단계로, 문서의 유효 루트 span 목록에 없다.

B. tool은 LLM이 인자를 만든 프로그램·서비스 호출이고 유효 루트 span이 아니다.

C. embedding은 임베딩을 반환하는 모델 호출용이며 유효 루트 span이 아니다.

D. `session_id`는 사용자 세션을 식별하는 인자일 뿐이다. span 종류의 루트 자격을 바꾸지 않는다.

E. 루트가 될 수 있는 종류는 llm, workflow, agent이다. 여러 단계(검색 후 생성)를 묶는 진입점에는 workflow가 맞다.

### A-11-1 · 팀별로 묶이지 않는 원인

단일 선택 · 케이스 · 도메인 ④ · L2 · 제품: Datadog

자료 1의 코드에서 비용 지표를 `team`별로 묶을 수 있게 하려면 어떻게 고쳐야 하는가?

A. 비용 지표는 커스텀 태그를 지원하지 않으므로, 팀별 분석은 지표 대신 트레이스 검색으로만 한다.

B. span 태그는 모든 `ml_obs.*` 지표에 자동 전파되므로 지표가 반영될 때까지 기다린다.

C. `cost_tags=["team", "request_id"]`를 추가해 두 태그를 모두 지표에 올린다.

D. `LLMObs.annotate` 호출에 `cost_tags=["team"]`을 추가한다.

E. `model_name`에 팀 이름을 붙여 `"gpt-5.1-teamA"`처럼 지정한다.

**상세 해설**

A. 비용·토큰 지표는 `cost_tags`로 지정한 태그를 커스텀 태그로 받을 수 있다.

B. span에 단 태그는 지표에 자동 전파되지 않는다. 문서는 span의 다른 태그가 지표 태그로 쓰이지 않는다고 안내한다.

C. `request_id`처럼 값이 끝없이 늘어나는 태그는 지표에서 잘리거나 빠질 수 있다. 팀·고객 등급·기능처럼 값의 범위가 제한된 태그만 쓰라고 한다.

D. 이미 `tags`에 있는 키를 `cost_tags`에 넘기면 그 키가 비용·토큰 지표의 태그로 전파되어 `team`별 집계가 가능해진다.

E. `model_name`은 공급자 가격표와 매칭하는 값이다. 임의로 바꾸면 모델명을 못 찾아 비용 추정이 실패한다.

### A-11-3 · 자체 호스팅 모델의 비용

### A-11-4 · annotation\_context와 cost\_tags의 적용 범위

단일 선택 · 케이스 · 도메인 ④ · L3 · 제품: Datadog

다른 서비스에서 OpenAI 호출이 자동 계측되고 있다. 아래 코드를 실행한 뒤의 결과로 옳은 것은?

```python
with LLMObs.annotation_context(
    tags={"team": "search"},
    cost_tags=["team", "feature"],
):
    client.chat.completions.create(...)   # openai 자동 계측 LLM span
```

A. `team`과 `feature`가 비용·토큰 지표와 `ml_obs.span.duration`에 모두 붙는다.

B. `tags`에 `feature`가 없어 예외가 발생하고, 애플리케이션 호출도 실패한다.

C. `team`이 비용·토큰 지표와 `ml_obs.span.duration`에 붙고, `feature`는 건너뛴다.

D. `annotation_context`는 수동 계측 span에만 적용되므로 자동 계측 span에는 `cost_tags`가 효과가 없다.

E. `team`은 비용·토큰 지표에 붙고, `feature`는 건너뛴다. `ml_obs.span.duration` 같은 다른 지표에는 둘 다 붙지 않는다.

**정답: E**

**상세 해설**

A. `feature`는 `tags`에 없어 건너뛰며, 커스텀 태그는 비용·토큰 지표에만 적용된다.

B. `tags`에 없는 키는 경고만 남기고 건너뛴다. ddtrace 4.16.0에서 실행해 예외 없이 건너뛰는 것을 확인했다.

C. `ml_obs.span.duration` 같은 지표에는 커스텀 태그가 적용되지 않는다.

D. `annotation_context`는 자동 계측 span을 수정하기 위한 기능이다.

E. `cost_tags`의 각 항목은 span 시작 시점의 `tags`에 있는 키여야 하므로 `feature`는 건너뛴다. 전파 대상은 비용·토큰 지표뿐이다.

### A-12-2 · Snowflake 사용자별 쿼터의 합산 상한

### A-12-4 · Databricks 청구 사용량 집계의 정정 행

단일 선택 · 케이스 · 도메인 ⑤ · L3 · 제품: Databricks

Databricks의 `system.billing.usage`에서 같은 시간 구간(10:00\~11:00)에 대한 원시 행이 아래와 같다. 이 표에는 정정(retraction)이 포함되어 있고, 음수 행은 원래 사용량을 상쇄하는 행이다. 아래 쿼리를 실행했을 때 결과는 무엇인가?

| usage\_metadata.job\_id | usage\_quantity |
| --- | --- |
| 11 | 12 |
| 11 | -12 |
| 11 | 9 |
| 22 | 5 |
| 33 | 4 |
| 33 | -4 |

```sql
SELECT usage_metadata.job_id, usage_start_time, usage_end_time,
       SUM(usage_quantity) AS usage_quantity
FROM system.billing.usage
GROUP BY ALL
HAVING usage_quantity != 0;
```

A. 6개 행이 그대로 반환된다. HAVING은 개별 행이 아니라 그룹 전체에만 적용되기 때문이다.

B. job 11은 12, job 22는 5, job 33은 4로 반환된다. 음수 행은 집계에서 제외된다.

C. job 11은 9, job 22는 5, job 33은 0으로 반환된다. HAVING은 합계가 0인 그룹도 보여 준다.

D. job 11은 9, job 22는 5만 반환되고 job 33은 결과에서 사라진다.

E. job 11은 21, job 22는 5만 반환되고 job 33은 사라진다. 정정 행은 양수만 더한다.

**정답: D**

**상세 해설**

A. GROUP BY ALL로 job과 시간 구간별로 묶이므로 6행이 그대로 나오지 않는다. HAVING은 그룹의 합계에 적용된다.

B. 음수 행도 SUM에 포함되어 원래 사용량을 상쇄한다. 정정을 무시한 값이 아니다.

C. HAVING이 usage\_quantity != 0이므로 합계가 0인 job 33은 제거된다. 0으로 반환되지 않는다.

D. job 11은 12 + (-12) + 9 = 9, job 22는 5, job 33은 4 + (-4) = 0이라 HAVING에서 제외된다. 문서의 예시 쿼리와 같은 방식이다.

E. 음수 행도 합산하므로 job 11은 21이 아니라 9다. 정정 행이 상쇄 값이라는 점을 놓친 계산이다.

## A-F01 · 빌드 시 사설 패키지 저장소 토큰 전달

단일 선택 · 코드 빈칸 · 도메인 ① · L1 · 제품: Docker

사설 PyPI 서버의 토큰을 이미지에 남기지 않고 빌드에 전달하려 한다. 빌드는 `docker build --secret id=pip_token,src=$HOME/.pip_token -t chat-app .`로 실행한다. 빈칸 \[A\], \[B\]에 들어갈 값으로 옳은 것은 무엇인가?

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=[A],id=pip_token \
    PIP_INDEX_URL="https://__token__:$(cat [B])@pypi.example.com/simple" \
    pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```

A. \[A\] = `type=bind`, \[B\] = `/run/secrets/pip_token`

B. \[A\] = `type=secret`, \[B\] = `/pip_token`

C. \[A\] = `type=secret`, \[B\] = `/run/secrets/pip_token`

D. \[A\] = `type=cache`, \[B\] = `/run/secrets/pip_token`

E. \[A\] = `type=secret`, \[B\] = `$HOME/.pip_token`

**정답: C**

**상세 해설**

A. `type=bind`는 빌드 컨텍스트 등을 마운트하는 유형이다. `--secret`으로 전달한 값을 쓰려면 `type=secret`이어야 한다.

B. 시크릿은 기본적으로 `/run/secrets/<id>` 파일로 마운트된다. `target` 옵션을 주지 않았으므로 `/pip_token`에는 파일이 없다.

C. `RUN --mount=type=secret,id=...`로 시크릿을 쓰며, 기본 마운트 경로는 `/run/secrets/<id>`다. 이 값은 해당 `RUN` 명령 동안만 사용 가능하고 이미지에 남지 않는다.

D. `type=cache`는 패키지 캐시처럼 빌드 간 유지되는 디렉터리를 위한 마운트이며 시크릿 전달용이 아니다.

E. `$HOME/.pip_token`은 호스트의 경로이고 `--secret`의 `src`에 쓴다. 빌드 컨테이너 안에서는 시크릿을 `/run/secrets/<id>`로 읽는다.

## A-F02 · HPA autoscaling/v2 매니페스트

```yaml
kind: HorizontalPodAutoscaler
metadata: {name: embed-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: embed-api}
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: [B]
        averageUtilization: 60
```

A. \[A\] = `v2beta2`, \[B\] = `Utilization`

B. \[A\] = `v2`, \[B\] = `AverageValue`

E. `Value`는 지표 전체 값을 목표 값과 비교하는 유형이어서 사용률(%)을 뜻하는 `averageUtilization`과 맞지 않는다.

## A-F03 · GPU를 요청하는 resources

```yaml
containers:
- name: vllm
```

C. \[A\] = `limits`, \[B\] = `nvidia.com/gpu`

## A-F04 · 느린 기동을 보호하는 probe

단일 선택 · 코드 빈칸 · 도메인 ② · L2 · 제품: Kubernetes

모델 적재에 최대 5분이 걸린다. 적재 중에는 liveness가 컨테이너를 죽이지 않게 하고, 적재가 끝난 뒤에는 아래 liveness 설정(10초 주기, 3회 실패)으로 교착을 빨리 감지하려 한다. 빈칸에 들어갈 값으로 알맞은 것은?

```yaml
containers:
- name: llm
  ports:
  - {name: http, containerPort: 8000}
  [B]:
    httpGet: {path: /healthz, port: http}
    periodSeconds: 10
    failureThreshold: [A]
  livenessProbe:
    httpGet: {path: /healthz, port: http}
    periodSeconds: 10
    failureThreshold: 3
```

A. \[A\] = `3`, \[B\] = `startupProbe`

B. \[A\] = `30`, \[B\] = `startupProbe`

C. \[A\] = `30`, \[B\] = `readinessProbe`

D. \[A\] = `30`, \[B\] = `livenessProbe`

E. \[A\] = `300`, \[B\] = `startupProbe`

**정답: B**

**상세 해설**

A. 10초 × 3 = 30초뿐이라 5분을 덮지 못한다. 적재가 끝나기 전에 startupProbe가 컨테이너를 죽인다.

B. startup 예산은 `failureThreshold × periodSeconds`이고 30 × 10 = 300초(5분)다. startupProbe가 성공하기 전에는 liveness가 실행되지 않고, 성공한 뒤에는 liveness가 이어받는다.

C. readinessProbe는 Service 트래픽 대상 여부만 정한다. liveness의 실행을 늦춰 주지 않으므로 적재 중 재시작은 막지 못한다.

D. `livenessProbe` 키가 아래와 중복되어 한쪽이 덮어써지거나 오류가 된다. 어느 쪽이든 startup 보호는 생기지 않는다.

E. `failureThreshold`는 시간이 아니라 연속 실패 횟수다. 300 × 10 = 3000초(50분)가 되어 교착된 기동도 50분 동안 방치된다.

## A-F05 · GPU가 가득 찬 상태의 롤링 업데이트

단일 선택 · 코드 빈칸 · 도메인 ⑤ · L3 · 제품: Kubernetes

GPU 노드 4대가 각각 GPU 1개를 쓰는 Pod 4개로 가득 차 있어 여유 GPU가 없다. 추가 Pod를 만들지 않고, 한 번에 최대 1개씩만 교체하며 롤링 업데이트가 진행되도록 하려 한다. 빈칸에 들어갈 값으로 알맞은 것은?

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: [A]
      maxUnavailable: [B]
  template:
    spec:
      containers:
      - name: llm
        resources:
          limits: {nvidia.com/gpu: 1}
```

A. \[A\] = `0`, \[B\] = `1`

B. \[A\] = `1`, \[B\] = `0`

C. \[A\] = `0`, \[B\] = `0`

D. \[A\] = `1`, \[B\] = `1`

E. \[A\] = `0`, \[B\] = `4`

**정답: A**

**상세 해설**

A. `maxSurge: 0`이면 정해진 수를 넘는 Pod를 만들지 않고, `maxUnavailable: 1`이면 기존 Pod 1개를 먼저 내려 GPU를 비운 뒤 그 자리에 새 Pod를 올린다. 추가 GPU 없이 한 번에 1개씩 진행된다.

B. 새 Pod를 먼저 하나 더 만들어야(surge) 하는데 여유 GPU가 없어 Pending에 머문다. `maxUnavailable: 0`이라 기존 Pod는 줄일 수 없어 롤아웃이 멈춘다.

C. 둘 다 0인 설정은 허용되지 않는다. 문서는 한쪽이 0이면 다른 쪽은 0일 수 없다고 정한다.

D. 초과 Pod 1개를 만들도록 허용하는 설정이라 "추가 Pod를 만들지 않는다"는 조건에 어긋난다. 그 Pod는 GPU가 없어 Pending 상태가 된다.

E. 기존 Pod 4개를 한꺼번에 내릴 수 있어 "한 번에 최대 1개" 조건에 어긋난다.

## A-F06 · alias로 모델 불러오기

```python
@workflow

@[A](name="vector_search")   # 벡터 DB에서 문서를 가져온다

@[B](model_name="claude", model_provider="anthropic")   # 모델 호출
```

## A-R01 · provider 서비스가 있는 compose 해석

단일 선택 · 코드·설정 해석 · 도메인 ① · L3 · 제품: Docker

Compose v2.36 이상에서 다음 compose.yaml로 `docker compose up`을 실행한다. (`docker compose config`로 문법 통과를 확인했다.)

```yaml
services:
  llm_provider:
    provider:
      type: model
      options:
        model: ai/gemma3
  api:
    image: registry.example.com/api:2.0
    depends_on:
      - llm_provider
  worker:
    image: registry.example.com/worker:2.0
```

동작에 대한 설명으로 옳은 것은 무엇인가?

A. Compose가 `llm_provider`라는 이름의 컨테이너를 pull 해서 `api`보다 먼저 띄운다.

B. `api`와 `worker` 모두에 `LLM_PROVIDER_` 접두사의 환경 변수가 주입된다.

C. 서비스 이름과 관계없이 주소가 항상 `MODEL_URL`이라는 이름의 변수로 주입된다.

D. `type: model`은 Compose에 내장된 이름이므로 외부 플러그인이나 바이너리 없이 처리된다.

E. Compose가 `docker-model` CLI 플러그인(또는 PATH의 `model` 바이너리)에 프로비저닝을 맡기고, 결과 정보는 `<서비스 이름>_<변수 이름>` 형태의 환경 변수로 `depends_on`을 선언한 `api`에만 전달된다.

**정답: E**

**상세 해설**

A. provider 서비스는 컨테이너가 아니라 플랫폼 기능을 나타내는 서비스이며 Compose가 이미지를 pull 해 띄우지 않는다.

B. 정보는 provider 서비스에 의존성을 선언한 서비스에 전달된다. `depends_on`이 없는 `worker`에는 전달되지 않는다.

C. 변수 이름은 `<PROVIDER_SERVICE_NAME>_<VARIABLE_NAME>` 규칙을 따른다. 서비스 이름이 접두사가 된다.

D. `type`은 Docker CLI 플러그인(예: `docker-model`) 또는 PATH의 바이너리, 혹은 실행 파일 경로를 가리킨다. `type: model`이면 `docker-model` 플러그인 또는 `model` 바이너리를 찾는다.

E. 문서가 설명하는 provider의 동작 그대로다. 플러그인이 옵션을 해석해 기능을 준비하고 접속 정보를 돌려주며, 이 정보가 의존하는 서비스에 환경 변수로 전달된다.

**근거 문서** https://github.com/docker/docs/blob/7efe900/content/manuals/compose/how-tos/provider-services.md · https://github.com/docker/docs/blob/7efe900/data/summary.yaml · 기준일 2026-10-20 · docker/docs 커밋 7efe900 · Docker Compose v5.5.1(`docker compose config` 문법 통과, `depends_on` 정규화 확인) · 검증 수준: 문서 대조

## A-R02 · 리소스 설정과 QoS 클래스

단일 선택 · 코드·설정 해석 · 도메인 ② · L2 · 제품: Kubernetes

다음 Pod의 QoS 클래스와, `embed` 컨테이너가 한도를 넘겨 쓰려 할 때의 동작으로 옳은 것은?

```yaml
apiVersion: v1
kind: Pod
metadata: {name: embed}
spec:
  containers:
  - name: embed
    image: registry.example/embed:1
    resources:
      requests: {cpu: "1", memory: 2Gi}
      limits: {cpu: "2", memory: 2Gi}
  - name: sidecar
    image: registry.example/sidecar:1
    resources:
      requests: {cpu: 100m, memory: 128Mi}
      limits: {cpu: 100m, memory: 128Mi}
```

A. Guaranteed이다. CPU 한도를 넘으면 스로틀링되고 메모리 한도를 넘으면 OOM kill 대상이 된다.

B. Burstable이다. CPU 한도를 넘으면 OOM kill 대상이 되고 메모리 한도를 넘으면 스로틀링된다.

C. Burstable이다. 두 한도 모두 스로틀링만 되고 컨테이너는 종료되지 않는다.

D. BestEffort이다. 한도가 있어도 커널이 강제하지 않는다.

E. Burstable이다. CPU 한도(2코어)에서는 스로틀링되고, 메모리가 한도(2Gi)를 넘으면 커널의 OOM kill 대상이 된다.

**정답: E**

**상세 해설**

A. Guaranteed는 Pod의 모든 컨테이너에서 CPU·메모리의 요청과 한도가 각각 같아야 한다. `embed`의 CPU는 요청 1, 한도 2로 달라서 `sidecar`가 조건을 채워도 Guaranteed가 아니다.

B. 강제 방식이 뒤바뀌었다. CPU는 스로틀링, 메모리는 OOM kill이다.

C. 메모리 한도는 커널의 OOM kill로 강제된다. 한도를 넘으면 컨테이너가 종료될 수 있다.

D. BestEffort는 어떤 컨테이너에도 요청과 한도가 전혀 없는 Pod다. 여기서는 값이 지정돼 있으므로 해당하지 않으며, 한도는 kubelet과 커널이 강제한다.

E. Guaranteed 조건을 채우지 못하지만 요청·한도가 지정된 컨테이너가 있으므로 Burstable이다. CPU 한도는 스로틀링으로, 메모리 한도는 OOM kill로 강제된다. 메모리 강제는 압박이 감지될 때 일어나는 사후 대응이라 즉시 죽지는 않을 수 있다.

**근거 문서** https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/ · https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/ · 기준일 2026-10-20 · kubernetes/website main · 검증 수준: 스키마·시그니처 확인 (매니페스트를 kubeconform strict와 V1Pod 모델로 검증, QoS 판정은 원문 기준 대조)

## A-R03 · Secret 값을 바꾸면 무엇이 갱신되는가

단일 선택 · 코드·설정 해석 · 도메인 ② · L2 · 제품: Kubernetes

Secret `llm-cred`의 `token` 값을 교체했다. Pod를 재시작하지 않고 충분히 기다렸을 때 새 값을 보게 되는 것은?

```yaml
apiVersion: v1
kind: Pod
metadata: {name: gateway}
spec:
  containers:
  - name: gw
    image: registry.example/gw:1
    env:
    - name: API_TOKEN
      valueFrom:
        secretKeyRef: {name: llm-cred, key: token}
    volumeMounts:
    - {name: cred, mountPath: /etc/cred}
    - {name: cred, mountPath: /etc/gw/token, subPath: token}
  volumes:
  - name: cred
    secret: {secretName: llm-cred}
```

A. `/etc/cred/token` 파일만 새 값으로 바뀐다.

B. `API_TOKEN` 환경 변수와 두 파일 모두 새 값으로 바뀐다.

C. `API_TOKEN` 환경 변수와 `/etc/cred/token`이 바뀌고 subPath 파일은 그대로다.

D. `/etc/cred/token`과 `/etc/gw/token`이 바뀌고 환경 변수만 그대로다.

E. 어느 것도 바뀌지 않는다. 사용 중인 Secret은 수정할 수 없다.

**정답: A**

**상세 해설**

A. 볼륨으로 마운트한 Secret은 결과적 일관성(eventually consistent) 방식으로 갱신된다. 환경 변수는 컨테이너가 재시작되어야 새 값을 보고, subPath 마운트는 자동 갱신을 받지 못한다.

B. 환경 변수는 컨테이너를 재시작하기 전에는 갱신되지 않는다.

C. 환경 변수가 갱신된다는 부분이 틀렸다. subPath 마운트가 갱신되지 않는다는 부분은 맞다.

D. subPath 마운트는 Secret 자동 갱신을 받지 못한다. 환경 변수가 갱신되지 않는다는 부분만 맞다.

E. `immutable: true`가 아닌 Secret은 수정할 수 있고, 변경은 볼륨에 반영된다. 이 Pod 예시에는 Secret이 immutable이라는 조건이 없다.

**근거 문서** https://kubernetes.io/docs/concepts/configuration/secret/ · https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/ · 기준일 2026-10-20 · kubernetes/website main · 검증 수준: 스키마·시그니처 확인 (매니페스트를 kubeconform strict와 V1Pod 모델로 검증, 갱신 동작은 원문 대조)

## A-R04 · 오래 걸리는 CronJob이 겹칠 때

단일 선택 · 코드·설정 해석 · 도메인 ⑤ · L2 · 제품: Kubernetes

다음 CronJob의 첫 Job이 00:00에 시작해 01:30에 끝난다. 이후 Job은 모두 1시간 30분이 걸린다고 가정할 때, 00:00부터 02:30 사이의 동작으로 옳은 것은?

```yaml
apiVersion: batch/v1
kind: CronJob
metadata: {name: eval-nightly}
spec:
  schedule: "0 * * * *"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: eval
            image: registry.example/eval:1.4
```

A. 01:00에 두 번째 Job이 병렬로 시작한다.

B. 01:00에 실행 중인 Job이 종료되고 새 Job으로 교체된다.

C. 01:00 실행은 건너뛰고, 01:30에 끝난 뒤에도 새 Job은 만들어지지 않으며, 02:00에 새 Job이 시작된다.

D. 01:00 실행은 건너뛰었다가 01:30에 첫 Job이 끝나는 즉시 한 번 실행된다.

E. 01:00 실행이 실패로 기록되고 CronJob이 자동으로 suspend된다.

**정답: C**

**상세 해설**

A. 병렬 실행은 `Allow`(기본값)의 동작이다. 이 CronJob은 `Forbid`다.

B. 실행 중인 Job을 새 Job으로 바꾸는 것은 `Replace`의 동작이다.

C. `Forbid`는 이전 실행이 끝나지 않았으면 새 실행을 건너뛴다. 이전 Job이 끝날 때도 `startingDeadlineSeconds`가 적용되는데, 01:00 슬롯은 01:30에는 이미 1800초가 지나 300초 데드라인을 넘었으므로 뒤늦게 실행되지 않는다. 다음 슬롯인 02:00에 새 Job이 시작된다.

D. 이전 Job이 끝난 뒤에도 데드라인이 적용된다. 300초 데드라인을 넘긴 01:00 슬롯은 01:30에 실행되지 않는다.

E. 건너뛴 실행은 놓친 일정으로 집계될 뿐이다. 실패로 기록되거나 자동으로 suspend되지 않는다.

**근거 문서** https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/ · 기준일 2026-10-20 · kubernetes/website main (최신 마이너 1.37) · 검증 수준: 스키마·시그니처 확인 (CronJob을 kubeconform strict와 V1CronJob 모델로 검증, 동작은 원문 대조)

## A-R05 · 청구 사용량 집계 결과 해석

단일 선택 · 코드·설정 해석 · 도메인 ⑤ · L3 · 제품: Databricks

정정이 반영된 `system.billing.usage`에서 잡별 사용량을 집계하는 쿼리와, 원본 행 일부가 아래와 같다. 쿼리 결과로 옳은 것은? (job\_id는 `usage_metadata.job_id`다)

```sql
SELECT usage_metadata.job_id, usage_start_time, usage_end_time,
       SUM(usage_quantity) AS usage_quantity
FROM system.billing.usage
GROUP BY ALL
HAVING usage_quantity != 0
```

| job\_id | usage\_start\_time | usage\_end\_time | usage\_quantity |
| --- | --- | --- | --- |
| 101 | 09:00 | 10:00 | 12.0 |
| 101 | 09:00 | 10:00 | -12.0 |
| 101 | 09:00 | 10:00 | 8.0 |
| 102 | 09:00 | 10:00 | 3.0 |
| 102 | 09:00 | 10:00 | -3.0 |
| 103 | 09:00 | 10:00 | 5.0 |
| 103 | 10:00 | 11:00 | 4.0 |

A. 4행: (101, 09\~10시, 8.0), (102, 09\~10시, 0.0), (103, 09\~10시, 5.0), (103, 10\~11시, 4.0)

B. 3행: (101, 09\~10시, 20.0), (103, 09\~10시, 5.0), (103, 10\~11시, 4.0)

C. 2행: (101, 09\~10시, 8.0), (103, 09\~11시, 9.0)

D. 3행: (101, 09\~10시, 12.0), (103, 09\~10시, 5.0), (103, 10\~11시, 4.0)

E. 3행: (101, 09\~10시, 8.0), (103, 09\~10시, 5.0), (103, 10\~11시, 4.0)

**정답: E**

**상세 해설**

A. HAVING이 합계가 0인 그룹을 걸러낸다. job 102는 3.0과 -3.0이 상쇄되어 0이므로 결과에 나오지 않는다.

B. 음수 행도 SUM에 포함된다. 101은 12.0 - 12.0 + 8.0 = 8.0이지 20.0이 아니다.

C. GROUP BY ALL은 job\_id뿐 아니라 시작·종료 시각도 그룹 키로 쓴다. 103의 두 시간대는 별도 행으로 남고 합쳐지지 않는다.

D. 정정으로 원본이 취소되고 정정값이 대신 들어간다. 101의 원본 12.0을 그대로 읽으면 안 되고 합계는 8.0이다.

E. 101은 12.0 - 12.0 + 8.0 = 8.0, 102는 합계 0이라 HAVING에서 제외, 103은 시간대가 달라 두 행이다. 문서의 설명대로 취소 행이 원본을 상쇄하고 정정 행의 값만 남는다.

## A-R06 · AI\_FILTER와 AI\_AGG를 함께 쓴 쿼리 해석

단일 선택 · 코드·설정 해석 · 도메인 ③ · L2 · 제품: Snowflake

상품 리뷰 테이블에 아래 쿼리를 실행했다. 리뷰 수는 그룹당 수만 건이며 한 그룹의 텍스트는 모델 컨텍스트 창보다 크다. 쿼리의 동작을 올바르게 설명한 것은 무엇인가?

```sql
SELECT category,
       AI_AGG(review, '불만 사항을 세 줄로 요약해 줘') AS summary,
       COUNT(*) AS n
FROM shop.reviews
WHERE AI_FILTER(PROMPT('이 리뷰는 부정적이다: {0}', review))
GROUP BY category;
```

A. AI\_FILTER는 SELECT 목록에서만 쓸 수 있어 WHERE에 두면 오류가 난다.

B. category마다 한 행이 나오고, 부정적이라고 판정된 리뷰만 모아 AI\_AGG가 문자열 summary를 만든다. n은 그 부정 리뷰의 개수다.

C. 컨텍스트 창을 넘는 그룹은 AI\_AGG가 앞부분만 잘라 요약하므로 summary가 일부 내용만 반영한다.

D. AI\_FILTER가 `{value, error}` 객체를 반환하므로 WHERE에서 불리언으로 쓸 수 없다.

E. summary는 `{error, response}` 구조의 객체로 반환되어 `:response`로 꺼내야 한다.

**정답: B**

**상세 해설**

A. AI\_FILTER는 BOOLEAN을 반환하며 문서에도 WHERE 절 예시가 있다.

B. WHERE로 부정 리뷰만 남긴 뒤 category별로 AI\_AGG가 문자열 하나를 반환하고 COUNT(\*)도 걸러진 행만 센다.

C. AI\_AGG는 모델 컨텍스트 창보다 큰 데이터셋도 지원하도록 설계되어 있다.

D. `{value, error}` 객체는 return\_error\_details를 TRUE로 줄 때의 형태다. 기본 호출은 BOOLEAN이다.

E. AI\_AGG는 결과 집계 문자열을 반환한다. `{error, response}`는 AI\_EXTRACT의 반환 형태다.

**근거 문서** https://docs.snowflake.com/en/sql-reference/functions/ai\_filter · https://docs.snowflake.com/en/sql-reference/functions/ai\_agg · 기준일 2026-10-20 · 문서 버전: 해당 없음(웹 문서) · 검증 수준: 문서 대조

## A-R07 · 모델 버전 별칭 승급 SQL 해석

단일 선택 · 코드·설정 해석 · 도메인 ⑤ · L3 · 제품: Snowflake

Snowflake Model Registry의 `FRAUD` 모델에서 아래 문장을 위에서부터 순서대로 실행했다. 처음 세 문장은 성공했다. V2를 챔피언으로 승급하려는 마지막 문장은 어떻게 되며, 승급을 성공시키는 방법은 무엇인가?

```sql
ALTER MODEL fraud VERSION v1 SET ALIAS = champion;
ALTER MODEL fraud VERSION v2 SET ALIAS = challenger;
ALTER MODEL fraud SET DEFAULT_VERSION = 'V2';
ALTER MODEL fraud VERSION v2 SET ALIAS = champion;   -- 결과는?
```

A. 성공한다. V1과 V2가 모두 champion 별칭을 갖게 되어 둘 중 최신 버전이 우선한다.

B. 성공한다. champion 별칭이 V1에서 V2로 자동 이동한다.

C. 실패한다. DEFAULT\_VERSION이 지정된 모델은 사용자 별칭을 바꿀 수 없다.

D. 성공한다. V2의 기존 challenger 별칭이 champion으로 바뀌고 DEFAULT 시스템 별칭이 해제된다.

E. 실패한다. champion은 이미 V1이 쓰고 있고 V2에는 challenger가 있다. `VERSION champion UNSET ALIAS`와 `VERSION challenger UNSET ALIAS`로 별칭을 풀고 다시 V2에 champion을 지정한다.

**정답: E**

**상세 해설**

A. 별칭 이름은 모델 안에서 유일해야 한다. 두 버전이 같은 별칭을 가질 수 없다.

B. 별칭은 자동으로 이동하지 않는다. 한 별칭은 한 버전에만 붙고, 옮기려면 먼저 해제해야 한다.

## A-R09 · 캐시 사용 시 비용 추정 오차

## A-T01 · 다이제스트로 고정한 베이스 이미지의 보안 패치

단일 선택 · 이론 · 도메인 ① · L3 · 제품: Docker

Dockerfile이 `FROM alpine:3.21@sha256:a8560b36...`처럼 태그와 다이제스트로 베이스 이미지를 고정하고 있다. 보안팀이 `alpine:3.21` 태그가 가리키는 이미지에 보안 패치가 반영됐다고 알린다. 개발자가 `docker build --pull --no-cache`로 다시 빌드한다. 올바른 판단은 무엇인가?

A. `--pull`이 태그의 최신 이미지를 받아오므로 패치된 베이스 이미지로 빌드된다.

B. `--no-cache`는 베이스 이미지까지 새로 받으므로 `--pull` 없이도 패치가 반영된다.

C. 다이제스트 고정은 보안 패치를 막는 설정이므로 고정을 완전히 제거하고 태그만 쓰는 것이 유일한 방법이다.

D. 다이제스트가 고정된 이상 두 플래그로는 같은 이미지가 쓰이므로 Dockerfile의 다이제스트를 새 값으로 갱신해야 하며, 갱신은 Dependabot PR이나 `docker scout recommendations`로 후보를 확인해 진행할 수 있다.

E. Docker Scout의 "No outdated base images" 정책을 켜면 다음 빌드부터 다이제스트가 자동으로 최신 값으로 바뀐다.

**정답: D**

**상세 해설**

A. 태그가 새 이미지를 가리켜도 다이제스트로 고정된 빌드는 고정된 이미지를 그대로 쓴다. `--pull`은 태그 기반 참조에서 새 버전을 확인하는 용도다.

B. `--no-cache`는 apt나 npm 같은 패키지 관리자의 최신 버전을 다시 받는 효과가 있지만 베이스 이미지를 새로 받지는 않는다. 베이스 갱신은 `--pull`의 역할이다.

C. 고정을 없애면 재현성과 감사 기록을 잃는다. 문서는 Dependabot 같은 도구로 태그와 다이제스트를 정해진 일정에 갱신하는 방법을 더 낫다고 안내한다. 유일한 방법이 아니다.

D. 문서는 다이제스트로 고정하면 태그가 바뀌어도 같은 이미지를 쓴다고 설명하며, 갱신 수단으로 Dependabot(`package-ecosystem: "docker"`)과 `docker scout recommendations`를 안내한다. 패치를 받으려면 고정된 다이제스트 값을 새 값으로 바꿔야 한다.

E. Scout 정책은 베이스 이미지(고정 다이제스트 포함)가 최신인지 평가해 비준수로 알려 줄 뿐이다. Dockerfile을 자동으로 고치지는 않는다.

## A-T02 · liveness 검사에 넣으면 안 되는 것

단일 선택 · 이론 · 도메인 ② · L2 · 제품: Kubernetes

LLM 게이트웨이(replicas 6)의 `/health` 엔드포인트는 벡터 DB 연결까지 확인하고, livenessProbe가 이 엔드포인트를 호출한다. DB 점검으로 30초간 연결이 끊기자 6개 Pod가 모두 재시작됐고, DB가 돌아온 뒤에도 한동안 서비스가 복구되지 않았다. 재발을 막는 설계는?

A. DB 연결 검사를 startupProbe로 옮긴다.

B. livenessProbe의 `timeoutSeconds`를 늘려 DB 점검 시간을 흡수한다.

C. readinessProbe를 제거하고 livenessProbe만 남긴다.

D. liveness는 앱 자체의 상태(교착 등)만 검사하고, DB 같은 백엔드 가용성 확인은 readinessProbe로 옮긴다.

E. Pod의 `restartPolicy`를 `Never`로 바꾼다.

**정답: D**

**상세 해설**

A. startupProbe는 기동 때만 실행된다. 운영 중에 DB가 끊기는 상황은 다루지 못한다.

B. 점검이 길어질수록 timeout을 키워야 하는 취약한 임시방편이며, 외부 의존성 장애가 재시작으로 이어지는 구조는 그대로다. 문서는 liveness를 잘못 구현하면 연쇄 장애가 날 수 있다고 경고한다.

C. readiness가 없으면 DB 장애 중에도 Pod가 계속 트래픽을 받아 오류만 응답한다. 문제의 원인은 liveness에 의존성 검사를 넣은 것이다.

D. 문서가 제시하는 패턴이다. liveness는 앱 자체가 건강할 때 통과하고, readiness는 필요한 백엔드가 사용 가능한지까지 확인한다. DB가 끊기면 Pod는 Service에서 빠질 뿐 재시작되지 않는다.

E. liveness 실패로 종료된 컨테이너는 restartPolicy의 적용을 받는다. Never로 바꾸면 재시작 없이 Pod가 죽은 채 남아 복구가 오히려 어려워진다.

## A-T04 · CPU 사용률 HPA가 움직이지 않는 이유

단일 선택 · 이론 · 도메인 ② · L2 · 제품: Kubernetes

`autoscaling/v2` HPA가 CPU `averageUtilization: 60`을 목표로 하고 metrics-server도 정상이다. 그런데 대상 Deployment의 컨테이너에는 메모리 요청만 있고 CPU 요청은 없으며, 부하가 아무리 높아도 레플리카가 늘지 않는다. 원인은?

A. 사용률을 CPU 한도(limit) 대비로 계산하는데 한도도 없어 계산할 수 없다.

B. 사용률은 CPU 요청 대비 비율이므로, 요청이 없으면 사용률이 정의되지 않아 HPA가 그 지표로는 아무 동작도 하지 않는다.

C. 요청이 없으면 노드 전체 코어 수 대비로 대신 계산되는데, 값이 항상 목표보다 낮게 나온다.

D. 요청이 없으면 기본 CPU 요청 100m가 자동 적용되어 사용률이 낮게 계산된다.

E. 메모리 요청이 있어서 HPA가 CPU 지표를 무시하고 메모리 기준으로 전환한다.

**정답: B**

**상세 해설**

A. 사용률은 한도가 아니라 요청 대비로 계산한다.

C. 노드 코어 수 대비로 대체 계산하는 동작은 없다.

## A-T05 · Secret을 안전하게 쓰기 위한 조치

단일 선택 · 이론 · 도메인 ② · L1 · 제품: Kubernetes

팀이 API 키를 Secret에 넣고 "값이 base64로 저장되니 안전하다"고 보고서에 적었다. 문서 기준으로 Secret을 안전하게 쓰기 위해 필요한 조치는?

A. base64 인코딩이 저장 시 암호화 역할을 하므로 추가 조치가 필요 없다.

B. Secret 대신 ConfigMap에 넣는다.

C. Secret을 `immutable: true`로 설정한다.

D. `data` 대신 `stringData` 필드로 값을 작성한다.

E. Secret의 저장 시 암호화(encryption at rest)를 켜고, RBAC로 Secret에 대한 접근을 최소 권한으로 제한한다.

**정답: E**

**상세 해설**

C. immutable은 값의 변경을 막고 클러스터 부하를 줄이는 기능이다. 값이 노출되는 것을 막지 못한다.

D. `stringData`는 base64 인코딩을 생략하게 해 주는 작성 편의 필드다. 저장되는 형태는 같다.

E. 문서가 안내하는 최소 조치다. Secret의 저장 시 암호화를 켜고 RBAC를 최소 권한으로 구성하며, 특히 `list`·`watch` 권한은 네임스페이스의 모든 Secret 값을 읽게 해 주므로 제한해야 한다.

B. `maxSurge`를 100%로 올린다.

C. `revisionHistoryLimit`을 0으로 둔다.

D. `minReadySeconds`를 120으로 둔다.

E. readinessProbe에 `initialDelaySeconds: 60`을 둔다.

E. Ready가 되는 시점을 60초 늦출 뿐이다. Ready가 된 뒤 90초 만에 크래시하는 패턴은 그대로 통과한다.

## A-T09 · 번들 배포 단계 구성

단일 선택 · 이론 · 도메인 ⑤ · L2 · 제품: Databricks

팀은 Declarative Automation Bundles(이전 이름 Databricks Asset Bundles)로 잡을 배포한다. PR마다 번들 구성 파일이 올바른지 먼저 점검하고, main 병합 뒤에는 dev 타깃에 반영한 다음 `hello_job`을 실행하려 한다. 알맞은 명령 구성은?

A. PR에서 `databricks bundle validate`, 병합 후 `databricks bundle deploy -t dev`에 이어 `databricks bundle run -t dev hello_job`

C. PR에서 `databricks bundle validate`, 병합 후 `databricks bundle run -t dev hello_job`만 실행

D. PR에서 `databricks bundle validate`, 병합 후 `databricks bundle deploy -t dev`만 실행하면 배포와 동시에 잡이 실행된다

C. `bundle run`은 잡 실행 단계이고 리소스를 만들거나 갱신하지 않는다. 배포 단계를 건너뛰면 변경된 번들 정의가 작업 공간에 반영되지 않는다.

D. 문서는 `bundle deploy`를 리소스 생성·갱신 단계로 설명하고 잡 실행은 별도의 `bundle run`으로 안내한다. 배포만으로 잡이 실행되지 않는다.

E. `bundle init`은 템플릿으로 새 번들 프로젝트를 만드는 명령이다. 기존 구성의 오류를 점검하는 용도가 아니다.

## A-T13 · 샘플링과 비용 지표

단일 선택 · 이론 · 도메인 ⑤ · L2 · 제품: Datadog

AI Observability의 청구가 span 전송량에 따라 늘어, Python SDK에서 `DD_LLMOBS_SAMPLE_RATE=0.1`을 적용했다. 재무팀은 `ml_obs.span.llm.total.cost`와 토큰 지표 대시보드로 LLM 지출을 추정한다. 샘플링을 적용한 뒤 이 지표는 어떻게 되는가?

A. 값이 약 10분의 1로 줄어, 실제 지출을 보려면 10배로 보정해야 한다.

B. 남긴 트레이스로만 집계하되, 샘플 비율을 반영해 자동 보정된다.

C. `ml_obs.span.duration`에만 영향이 있고 비용·토큰 지표는 영향이 없다.

D. 영향이 없다. 지표는 샘플링과 무관하게 전체 트래픽을 기준으로 계산된다.

E. 샘플링을 켜면 자동 단가 계산이 꺼져 비용 지표가 만들어지지 않는다.

**정답: D**

**상세 해설**

A. 샘플링은 지표를 줄이지 않는다. 보정할 필요가 없다.

B. 지표는 남긴 트레이스만으로 집계하지 않으며, 샘플 비율 보정이라는 동작도 없다.

C. `ml_obs.*` 지표 전반이 샘플링 영향을 받지 않는다. `ml_obs.span.duration`도 마찬가지다.

D. 샘플링으로 버려지는 span은 Datadog이 트레이스를 받은 뒤 걸러지므로, 비용·토큰을 포함한 `ml_obs.*` 지표는 샘플 비율과 상관없이 전체 트래픽 기준이다. 샘플링은 span 저장량(청구)을 줄이는 수단이다.

E. 자동 비용 계산은 샘플링 설정과 무관하게 동작한다.

- 검증 수준: 스키마·시그니처 확인 2(A-F08, A-F09), 문서 대조 15, 실행 확인 0. Snowflake 계정이 없어 SQL과 REST 호출은 실행하지 못했고 문서 본문 대조로 갈음했다. snowflake-ml-python 2.5.0과 snowflake 1.13.2를 venv에 설치해 log\_model·search 시그니처, Registry.get\_model, Model.default 세터를 확인했다.
- 약한 근거: A-09-4의 "TARGET\_LAG는 원본 보존 기간보다 짧게"는 CREATE CORTEX SEARCH SERVICE 페이지의 Note에서 확인했다. 다만 Cortex Search 개요 페이지는 이 둘의 관계를 서술하지 않는다. 같은 문항의 "질의 롤은 서비스 USAGE(+DB·스키마 USAGE)만 필요하고 원본 SELECT는 불필요"는 개요 페이지의 owner's rights 서술과 질의 권한 서술에서 추론한 것이며 "원본 SELECT 불필요"를 직접 명시한 문장은 확인하지 못했다.
- A-08-4: AI\_COMPLETE의 named argument 호출(show\_details => TRUE)은 문서의 "positional 또는 named" 서술에 근거했고 실행하지 못했다. TRY\_COMPLETE의 return\_error\_details 대응은 AI\_COMPLETE 페이지에 서술이 없어 문항에서 쓰지 않았다.
- A-08-2: 이전 함수 CLASSIFY\_TEXT의 반환 키가 `label`이라는 것은 지문이 주는 기존 코드 전제로만 다뤘다(문서 대조 불가). 마이그레이션 문서는 출력 형식이 바뀐다는 사실만 확인했다.
- A-R07: DEFAULT\_VERSION 설정이 별칭 변경을 막지 않는다는 점은 ALTER MODEL 페이지에 제한이 적혀 있지 않다는 점에 근거한 오답 이유다(C 선택지). 실행 확인 불가.
- A-12-1·A-T10에서 Cortex Analyst가 예산 미지원이라는 사실(T10 E)과 리소스 모니터 한계(A-12-1 A·D, T10 C)는 오답 이유로 겹쳐 쓰였다. 정답 근거는 서로 다르다(쿼터 평가 지연 vs 리소스 모니터 한계).
- A-12-3의 "예산 알림 최대 4개", A-12-4의 정정 행 구조(record\_type 열은 사용하지 않음)는 Databricks 문서 본문에서 확인했다. AI Gateway(legacy) 가드레일 등 출제 제외 항목과 두 개의 충돌하는 Snowflake 사용량 뷰 이름, model!PREDICT, 다중 인덱스, AUTO\_SUSPEND(Cortex Search)는 정답 근거로 쓰지 않았다.
